# 브랜드·상품 삭제에 동기 호출과 비관적 잠금을 선택한 이유

처음에는 삭제되지 않은 상품이 남아 있는 브랜드의 삭제를 거절했다. 이후 요구사항이 바뀌었다. 브랜드를 삭제하면 연결된 상품도 함께 삭제하고, 둘은 같은 성공과 실패로 묶어야 했다. 이 조건을 지키기 위해 하나의 트랜잭션 안에서 삭제 포트를 동기적으로 호출하고, 경쟁하는 쓰기에는 비관적 잠금을 적용하기로 했다.

## 애그리거트는 나누고 트랜잭션은 함께

`Brand`와 `Product`는 별도 애그리거트로 유지했다. 상품에는 가격 수정, 재고 수정, 주문 확정 같은 독립적인 작업이 있다. 브랜드 삭제 요구 하나를 위해 상품 전체를 브랜드의 내부 구성원으로 옮길 이유는 부족했다. 대신 이 유스케이스는 여러 애그리거트를 하나의 로컬 DB 트랜잭션에서 바꾸는 명시적인 예외로 두었다.

브랜드 쪽에서 필요한 `ProductDeleter` 포트를 선언하고 상품 애플리케이션 서비스가 구현한다. 브랜드 삭제 메서드의 흐름은 다음과 같다.

```kotlin
val brand = brandFinder.findForUpdate(id)
productDeleter.deleteAllOfBrand(brand.id)
brand.delete()

brandRepository.save(brand)
```

상품 삭제도 브랜드 삭제의 쓰기 트랜잭션에 참여한다. 동기 호출만으로 원자성이 생기는 것은 아니다. 같은 트랜잭션을 사용하고, 실패가 롤백으로 이어지도록 예외 전파와 롤백 규칙도 맞아야 한다. 직접 호출하면 필수 작업의 순서와 책임이 메서드 본문에 드러난다.

삭제는 행을 지우지 않고 삭제 시각을 기록하는 논리 삭제다. 기존 주문과 좋아요의 참조를 보존하면서, 재고가 0인 상품까지 함께 삭제한다. 이미 삭제된 상품의 삭제 시각은 바꾸지 않는다.

## 비동기 이벤트를 선택하지 않은 이유

`@Async`와 `@TransactionalEventListener`를 조합하면 완료의 의미가 달라진다. 리스너의 기본 실행 시점은 `AFTER_COMMIT`이다. 따라서 브랜드 트랜잭션이 커밋된 뒤 상품 삭제가 다른 스레드의 별도 트랜잭션에서 실행된다. [Spring 트랜잭션 이벤트 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html), [Spring 트랜잭션 문서](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/transaction/annotation/Transactional.html)

이때 보장되는 것은 **리스너가 실행될 때 앞선 트랜잭션이 이미 커밋되었다는 조건**이다. 리스너가 반드시 실행되거나 상품 삭제 트랜잭션이 성공한다는 보장은 아니다. 브랜드 커밋 직후 애플리케이션이 중단될 수도 있고, 상품 삭제가 실행되다가 실패할 수도 있다. 어느 경우든 이미 커밋된 브랜드 삭제는 뒤의 실패로 롤백할 수 없다. 이런 실패를 복구하려면 작업을 영속적으로 기록하고 재처리하는 장치가 필요하다. [Spring Modulith 이벤트 발행 레지스트리](https://docs.spring.io/spring-modulith/reference/events.html#_the_event_publication_registry)

동기 이벤트나 `BEFORE_COMMIT` 리스너라면 같은 트랜잭션을 유지할 수 있다. 하지만 짧고 필수적인 이 흐름에서는 직접 호출하는 편이 작업 시점과 잠금 순서를 읽기 쉬웠다.

## 동시 요청은 첫 조회부터 잠근다

원자성을 지켜도 낡은 값을 덮어쓰는 문제는 남는다. 잠금 없이 주문 확정이 삭제 전에 읽어 둔 상품을 나중에 저장하면, 현재 Hibernate 매핑에서는 옛 삭제 시각으로 덮어쓸 수 있다. 반대로 삭제가 주문 확정의 재고 차감을 덮어쓸 수도 있다.

그래서 상품을 수정하거나 삭제하거나 재고를 차감하는 모든 경로는 **쓰기 판단에 사용할 첫 조회부터 배타 잠금을 얻도록** 했다. 삭제만 잠그고 다른 쓰기는 평소처럼 읽게 두어서는 부족하다. Hibernate가 이미 관리하는 엔티티의 낡은 필드는 나중에 잠금을 얻는다고 자동으로 최신 값으로 바뀌지 않기 때문이다.

상품 등록에는 별도의 보호가 필요하다. 아직 없는 상품 행 대신, 삭제되지 않은 브랜드를 공유 잠금으로 읽는다. 브랜드 삭제는 같은 브랜드 행에 배타 잠금을 얻는다. 여러 등록은 함께 진행할 수 있지만, 삭제와는 순서가 정해진다.

등록이 먼저 잠그면 삭제가 기다렸다가 새 상품까지 함께 삭제한다. 삭제가 먼저 잠그면 등록이 기다린 뒤 삭제된 브랜드를 확인하고 거절된다. 외래 키만으로는 이 규칙을 지킬 수 없다. 논리 삭제는 브랜드 행을 남기므로 참조 자체는 여전히 유효하기 때문이다.

브랜드 삭제에서는 브랜드를 먼저 잠그고 상품은 id 오름차순으로 잠근다. 상품 조회의 `ORDER BY`만으로 실제 잠금 획득 순서가 보장되는 것은 아니므로, `brand_id` 인덱스와 실행 계획도 중요하다. 주문 확정의 상품 조회에는 브랜드를 함께 잠그지 않아, 같은 브랜드의 서로 다른 상품을 주문하는 요청끼리 불필요하게 기다리지 않게 했다. 잠금은 커밋이나 롤백까지 유지된다. [MySQL 잠금 읽기 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

낙관적 잠금도 고려했지만, 상품 하나의 충돌로 브랜드 삭제 전체가 실패하면 연쇄 작업을 통째로 재시도해야 한다. 이 흐름에서는 작업을 진행한 뒤 충돌을 발견하는 것보다, 먼저 기다리고 최신 상태로 판단하는 방식이 더 직접적이라고 보았다.

## 상품이 많아지면 무엇을 다시 볼까

이 선택에는 대가가 있다. 경쟁하는 쓰기를 기다리고, 상품이 많으면 많은 잠금을 완료 시점까지 유지한다. JDBC 배치는 UPDATE의 왕복 비용을 줄이지만 배치 사이에 잠금을 풀어 주지는 않는다. 비용이 커지면 도메인의 삭제 규칙과 영속성 컨텍스트 처리를 함께 검토하며 벌크 UPDATE도 살펴볼 수 있다.

비동기 처리 역시 다시 볼 수 있다. 다만 같은 큰 트랜잭션을 백그라운드로 옮기는 것만으로는 DB 부담이 줄지 않는다. 작은 트랜잭션으로 나누려면 일부 상품만 먼저 삭제된 상태를 허용하고, API가 말하는 완료의 의미도 바꿔야 한다.

그때는 브랜드를 `DELETING` 상태로 두고 새 상품 등록과 판매를 막으면서, 같은 트랜잭션에서 정리 작업을 영속적으로 기록해야 한다. 반복 실행해도 안전한 처리, 재시도와 복구 상태 확인도 필요하다. 상품 수를 재검토 조건으로 논의했지만 특정 개수의 기준을 정하지는 않았다.

지금은 전체 작업을 함께 커밋하거나 롤백하는 완료 기준을 유지하기로 했다. 실제 처리 시간이나 다른 요청의 잠금 대기가 감당하기 어려워지면, 그 측정 결과를 바탕으로 삭제 계약과 복구 절차를 함께 다시 설계하려 한다.
