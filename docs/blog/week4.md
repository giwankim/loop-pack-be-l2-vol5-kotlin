# 상품 목록의 두 병목: 인덱스로 없앤 정렬과 캐시로 건너뛴 집계

4주차 과제는 캐시를 붙이기 전에 병목부터 증명하라고 했다. 대상은 이미 있던 고객 상품 목록 `GET /api/v1/products`다. 필터, 정렬, 페이지, 삭제 조건은 그대로 두고 줄여야 했다. 성능 비교를 위해 다른 인덱스를 지워서도 안 됐다.

재 보니 병목은 둘이었고 처방이 달랐다. 브랜드를 골라 가격 낮은순으로 보는 첫 페이지는 그 브랜드의 상품을 모두 읽고 정렬했다. 이것은 인덱스로 정렬 단계를 없앴다. 브랜드 없이 전체 카탈로그를 좋아요 많은순으로 보는 첫 페이지는 좋아요 12만 행을 세어 정렬했다. 센 값으로 정렬하므로 인덱스로는 없앨 수 없었다. 이것은 Redis 캐시로 건너뛰게 했다.

| 요청 | 병목 | 처방 | 효과 | 새로 생긴 비용 |
| --- | --- | --- | --- | --- |
| 브랜드 + `price_asc` 첫 페이지 | 브랜드의 상품을 모두 읽고 정렬 | `(brand_id, price, id DESC)` 인덱스 | 읽는 행 2,000 → 22(브랜드 101), 정렬 단계 없음 | 상품 등록과 가격 수정이 인덱스 하나를 더 고침 |
| 전체 카탈로그 `likes_desc` 첫 페이지 | 좋아요 123,255행의 조인과 집계 정렬(DB 안 91.8 ms) | 목록 캐시, DB의 revision 행 하나로 무효화 | p50 93.1 → 2.1 ms(miss → hit) | hit에도 SQL 1개, 목록을 바꾸는 쓰기가 모두 한 행에서 줄을 섬 |

두 처방 모두 가장 오래 고민한 것은 빠르기가 아니었다. 3주차에 세운 잠금의 차례를 깨지 않는 것이었다.

## 먼저 잰 것

재현할 수 있는 seed를 Kotlin으로 만들었다. 브랜드는 101개이고 그중 2개는 삭제되었다. 상품은 12,000개이고, 그중 2,000개가 큰 브랜드 101에 몰려 있다. 사용자는 1,000명, 좋아요는 126,955개다. 가격과 브랜드는 과제가 예시로 든 식을 그대로 썼다. 삭제된 상품, 품절 상품, 좋아요가 없는 상품, 동점도 일부러 넣었다. 데이터는 Testcontainers의 MySQL 8.4에 넣고, 넣은 뒤 `ANALYZE TABLE`로 통계를 새로 만들었다.

계획은 직접 적은 SQL로 보지 않았다. 애플리케이션이 실제로 보낸 SQL을 테스트 안에서 잡아 같은 바인드 값으로 `EXPLAIN ANALYZE`했다. 요청 하나가 보내는 SQL은 둘이다. 브랜드를 fetch join한 페이지 쿼리, 그리고 그 페이지 상품 20개의 좋아요 수를 `in (…)`으로 한 번에 세는 쿼리다. 가격순의 페이지 쿼리는 다음과 같다(컬럼은 줄였다).

```sql
select … from product p1_0
join brand b1_0 on b1_0.id = p1_0.brand_id and (b1_0.deleted_at is null)
where (p1_0.deleted_at is null) and b1_0.id = ?
order by p1_0.price, p1_0.id desc
limit ?, ?   -- 0, 21: 20개를 보여 주고 1개로 다음 페이지가 있는지 본다
```

기존 스키마에서 MySQL은 `brand_id` 인덱스로 그 브랜드의 상품을 모두 읽었다. 삭제된 상품을 거르고 정렬한 뒤 21행을 잘랐다.

```
-> Limit: 21 row(s)
    -> Sort: p1_0.price, p1_0.id DESC, limit input to 21 row(s) per chunk
        -> Filter: (p1_0.deleted_at is null)
            -> Index lookup on p1_0 using IDX_PRODUCT_ON_BRAND_ID (brand_id=7)   rows=100
```

브랜드 7은 100행을 읽고 0.298 ms가 걸렸다. 브랜드 101은 2,000행을 읽고 1.22 ms가 걸렸다. 브랜드가 커지면 읽고 정렬할 행도 같이 늘어난다.

전체 카탈로그 `likes_desc`는 자릿수가 달랐다. 삭제되지 않은 상품 11,444개마다 좋아요를 인덱스로 찾아 123,255행을 조인하고, 11,444그룹을 임시 테이블로 집계한 뒤 정렬한다. DB 안에서 91.8 ms, 요청 하나의 p50이 85.2 ms였다.

두 측정이 이후의 선택을 갈랐다. 가격순은 읽는 행이 브랜드의 크기를 따르는 것이 문제라서 인덱스로 풀 수 있다. `likes_desc`는 집계가 문제라서 인덱스로는 풀 수 없고, 캐시할 조회로 이것을 골랐다.

## 가격순: `id DESC`까지 적어야 했던 이유

목록의 차례는 `price ASC, id DESC`다. 같은 가격이면 늦게 등록된 상품이 앞선다. 처음 떠오르는 인덱스는 `(brand_id, price)`인데, 이 인덱스로는 정렬이 사라지지 않는다.

InnoDB의 보조 인덱스는 항목 끝에 기본 키를 붙인다. 그래서 `(brand_id, price)`는 실제로 `(brand_id, price, id)`의 오름차순으로 저장된다. 앞으로 읽으면 `price ASC, id ASC`이고, 뒤로 읽으면 `price DESC, id DESC`다. 어느 쪽으로 읽어도 방향이 섞인 `price ASC, id DESC`는 나오지 않는다. 미리 해 본 탐침에서도 이 인덱스를 두었을 때 정렬이 남았다. [InnoDB 클러스터드·보조 인덱스](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html), [ORDER BY 최적화](https://dev.mysql.com/doc/refman/8.4/en/order-by-optimization.html)

MySQL 8은 인덱스의 열마다 내림차순을 저장할 수 있다. `id DESC`를 명시하면 인덱스의 차례가 목록의 차례와 같아진다. [내림차순 인덱스](https://dev.mysql.com/doc/refman/8.4/en/descending-indexes.html) 엔티티에는 주문 목록 인덱스와 같은 표기로 선언했다.

```kotlin
Index(name = "IDX_PRODUCT_ON_BRAND_ID_AND_PRICE_AND_ID", columnList = "brand_id, price, id DESC")
```

이제 MySQL은 인덱스를 앞에서부터 읽으며 삭제된 상품만 거르고, 21행이 차면 멈춘다.

```
-> Limit: 21 row(s)
    -> Filter: (p1_0.deleted_at is null)
        -> Index lookup on p1_0 using IDX_PRODUCT_ON_BRAND_ID_AND_PRICE_AND_ID (brand_id=7)   actual rows=22
```

22행을 읽은 것은 앞쪽 22개 가운데 하나가 삭제된 상품이었기 때문이다. 브랜드 101도 똑같이 22행을 읽었다. 읽는 행의 수가 브랜드의 상품 수가 아니라 페이지 크기를 따르게 되었다.

## 기존 인덱스를 지우지 않은 이유: 잠금의 차례

새 인덱스는 `brand_id`로 시작하므로 기존 `brand_id` 단독 인덱스는 그 앞부분처럼 보인다. 중복이라 지우고 싶어진다. 하지만 지우면 3주차에 세운 규칙이 깨진다.

3주차에 브랜드를 삭제하면 그 브랜드의 상품을 `FOR UPDATE`로 잠그고 함께 삭제하게 했다. 교착을 피하려고 모든 경로가 상품을 id 오름차순으로 잠근다는 규칙도 두었다. 그런데 InnoDB의 잠금 읽기는 `ORDER BY`의 차례가 아니라 **훑는 인덱스의 차례**로 행을 잠근다. 단독 인덱스는 끝에 붙은 기본 키 때문에 id 차례로 읽히고, 그래서 id 차례로 잠긴다. [잠금 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

단독 인덱스를 지우면 MySQL이 외래 키를 받치는 데 `brand_id`로 시작하는 복합 인덱스를 쓴다. [외래 키 제약](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) 브랜드 삭제의 잠금 읽기도 그 인덱스를 따라 읽고, 상품이 가격 차례로 잠긴다.

`(brand_id, deleted_at, price, id DESC)`도 검토했다. 삭제 조건까지 인덱스로 걸러 가격순에서는 정확히 21행만 읽는다. 하지만 탐침에서 옵티마이저는 브랜드 삭제의 잠금 읽기에 이 인덱스를 골랐다. `performance_schema.data_locks`를 보니 가장 싼 상품부터 잠겼다. 계획에는 `Sort: p1_0.id`가 붙어 있었지만, 이 정렬은 돌려줄 행의 차례만 바꿀 뿐 이미 걸린 잠금의 차례는 바꾸지 못한다. 브랜드의 좋아요 많은순도 이 인덱스로 옮겨 가 0.54 ms에서 0.90 ms로 느려졌다. 논리 삭제는 `deleted_at`을 바꾸므로 삭제할 때마다 인덱스도 고쳐야 했다.

그래서 단독 인덱스를 남기고 그 이유를 엔티티의 KDoc에 적었다. 테스트로도 지킨다. 큰 seed 위에서 실제 브랜드 삭제를 롤백할 트랜잭션 안에서 실행해 잠금 읽기 SQL을 잡고, 그 계획에 정렬 단계가 없는지 단언한다. 정렬 없이 `ORDER BY id`에 답하는 계획은 id 차례로 읽고, 그 차례로 잠근다. `(brand_id, deleted_at, price, id DESC)`를 더해 보면 이 테스트는 `Sort: p1_0.id`를 내며 실패했다.

## 인덱스 전후를 한 실행 안에서 비교하기

인덱스를 지웠다가 다시 만들지 않았다. 인덱스를 `INVISIBLE`로 바꾼 상태를 "전", `VISIBLE`로 되돌린 상태를 "후"로 두었다. 옵티마이저는 숨긴 인덱스를 보지 않지만, 쓰기는 계속 그 인덱스를 고친다. 그래서 같은 seed와 같은 통계 위에서 인덱스 하나만 달라진다. [보이지 않는 인덱스](https://dev.mysql.com/doc/refman/8.4/en/invisible-indexes.html) 이 DDL은 열린 트랜잭션을 암묵적으로 커밋하므로 테스트는 롤백 트랜잭션 밖에서 돌고, 실패해도 `finally`에서 인덱스를 다시 보이게 한다.

빨라졌다는 것만으로는 개선이라고 보지 않았다. 두 상태의 응답 본문이 seed에서 따로 계산한 기대값과 엄격하게 같아야 하고, 서로 글자까지 같아야 한다. 첫 페이지 전체가 1,000원 한 가격인 브랜드 101에서는 동점 규칙만이 차례를 정한다. 인덱스의 `id DESC`가 그 규칙을 그대로 지켰다.

| 요청 | 상태 | 읽은 행 | 정렬 | DB 안 시간 | 지연 p50 (준비 50, 표본 200) |
| --- | --- | --- | --- | --- | --- |
| 브랜드 7 | 전 | 100 | 있음 | 0.298 ms | 6.724 ms |
| 브랜드 7 | 후 | 22 | 없음 | 0.073 ms | 5.870 ms |
| 브랜드 101 | 전 | 2,000 | 있음 | 1.22 ms | 5.369 ms |
| 브랜드 101 | 후 | 22 | 없음 | 0.101 ms | 3.380 ms |

요청 하나의 지연은 DB 안 시간만큼 줄지 않았다. MockMvc로 잰 지연에는 디스패치, 검증, JSON 직렬화, 두 SQL의 왕복이 모두 들어 있고, 페이지 쿼리는 그중 작은 몫이다. 그래서 차이는 DB 안에서 1 ms 넘게 줄어든 브랜드 101에서만 분명하게 보였다. 지연의 꼬리는 실행마다 크게 흔들렸다. 브랜드 7 "후"의 p99가 한 실행에서는 33.6 ms, 다른 실행에서는 5.6 ms였다. 그래서 시간은 출력만 하고 단언하지 않는다. 이 인덱스의 진짜 효과는 읽는 행이 브랜드의 크기를 따르지 않게 된 것이다.

## 인덱스로 안 되는 것: 센 값으로 하는 정렬

`likes_desc`의 차례는 좋아요 수다. 좋아요 수는 저장된 열이 아니라 관계를 세어 얻는 값이다. 세기 전에는 차례를 알 수 없으므로, 어떤 인덱스도 이 정렬을 대신하지 못한다.

좋아요 수를 상품 행에 저장하면 정렬은 인덱스로 풀린다. 대신 누를 때와 취소할 때마다 상품 행을 고치는 쓰기가 생긴다. 행을 고치면 그 행을 잠그므로, 잠그지 않던 좋아요가 주문 확정, 재고 수정과 같은 상품 행에서 줄을 서게 된다. 주문 확정은 상품 행을 처음 읽을 때부터 commit까지 쥔다. 이번에는 좋아요 수를 계속 관계에서 세고, 대신 이 목록을 캐시하기로 했다.

## 캐시할 것과 하지 않을 것

고객 상품 목록 한 경로를 캐시한다. 필터, 정렬, 페이지, 크기의 모든 조합이다. 검증을 지난 요청은 빈 목록도 캐시하고, 400 오류는 캐시하지 않는다.

- **값:** 고객 응답이 내보내는 필드만 담은 투영이다. 재고 수량과 등록·수정 시각은 뺐다. 품절을 바꾸지 않는 재고 쓰기는 캐시를 무효로 만들지 않으므로, 수량을 담으면 캐시된 값이 틀린 값을 들게 된다.
- **사용자:** 목록에는 사용자별 필드가 원래 없다. 그래서 키에도 사용자가 없다.
- **키:** `product-list::v1:{revision}:{brandId|all}:{sort}:{page}:{size}`. `v1`은 값의 모양이 바뀌면 올린다. `{revision}`은 아래에서 설명한다.
- **TTL:** 5분. 옛 키를 치우는 용도일 뿐 신선도의 상한이 아니다.
- **캐시하지 않은 것:** 상품 상세는 기본 키 조회와 좋아요 수 하나라서 싸다. 관리자 목록은 재고 수량을 싣는다. 내 좋아요 목록은 사용자마다 다르다.

## TTL이나 키 삭제로는 모자란 이유

과제가 정한 계약은 셋이다. 정상 변경이 commit한 뒤 시작한 조회는 바뀐 결과를 받는다. 되돌린 변경의 결과는 게시하지 않는다. 삭제된 상품은 캐시를 거쳐서도 보이지 않는다.

- **TTL만 둔다.** 변경 뒤에도 TTL이 끝날 때까지 옛 결과가 나간다. 삭제된 상품도 그동안 보인다.
- **트랜잭션 안에서 키를 지운다.** 지운 뒤 commit 전에 시작한 조회가 commit 전의 결과로 키를 다시 채운다.
- **commit 뒤에 키를 지운다.** 지우기가 실패하면 TTL까지 옛 결과가 남는다. 더 까다로운 것은 늦은 채움이다. 옛 조회가 DB에서 5,000원을 읽는다. 관리자가 1,000원으로 바꾸고 commit한 뒤 키를 지운다. 옛 조회가 5,000원을 키에 쓴다. 다음 조회가 읽는 바로 그 키다.

모든 조합을 캐시하므로 지울 키를 찾는 것도 문제다. `@CacheEvict(allEntries = true)`는 Redis에 `KEYS`를 보낸다.

## DB의 revision 행 하나로 무효화하기

키를 지우는 대신 키를 바꾸기로 했다. DB에 상품 목록의 revision을 담는 행을 하나 두고, 목록을 바꾸는 쓰기는 자기 트랜잭션 안에서 그 값을 하나 올린다. `insert … on duplicate key update revision = revision + 1` 한 문장이다. 목록은 읽기 전용 트랜잭션의 첫 문장으로 revision을 읽고, 그 값을 넣어 키를 만든다.

이렇게 하면 세 계약이 DB의 트랜잭션 규칙에서 따라 나온다.

- commit한 변경은 revision을 올렸으므로, 그 뒤에 시작한 조회는 새 키를 읽는다. 옛 키에는 아무도 오지 않는다.
- commit하지 않은 revision은 다른 트랜잭션에 보이지 않는다. 되돌린 변경의 revision으로 채워지는 키가 없다.
- 늦게 끝난 옛 조회는 자기가 읽은 옛 revision의 키에 쓴다. 새 조회는 그 키를 읽지 않는다.

한 키에 한 시점의 결과만 담기는 것도 중요하다. REPEATABLE READ에서 스냅샷은 트랜잭션의 첫 읽기에서 정해진다. [일관된 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html) revision을 첫 문장으로 읽으므로, miss에서 뒤따르는 페이지 쿼리와 좋아요 수 조회는 그 revision과 같은 상태를 본다. 그래서 같은 키를 동시에 채우는 조회들은 같은 값을 쓴다. 반대로 페이지를 먼저 읽고 revision을 나중에 읽으면, 그 사이 commit한 변경 전의 페이지가 새 키에 들어간다.

Spring의 `@Cacheable`에서는 키 생성기가 revision을 읽는다. [캐시 애노테이션](https://docs.spring.io/spring-framework/reference/integration/cache/annotations.html) 그러려면 트랜잭션이 캐시보다 바깥이어야 한다. `@EnableTransactionManagement`의 order를 정해 트랜잭션 advisor가 캐시 advisor를 감싸게 했고, 키 생성기는 트랜잭션이 없으면 실패한다.

Redis는 쓰기 경로에서 빠졌다. 쓰기는 Redis에 아무것도 보내지 않으므로, commit 뒤에 실패할 무효화 호출이 없다. 늦은 채움은 테스트로 재현했다. 옛 조회를 DB를 읽은 뒤 캐시 쓰기 앞에서 멈추고, 가격 수정(5,000 → 1,000)을 commit한 뒤 옛 조회를 풀었다. 옛 결과가 옛 키에 들어간 뒤에도 새 조회는 1,000원을 돌려준다. 키의 revision을 상수로 바꿔 보면 마지막 조회가 5,000원을 돌려주며 실패한다.

revision을 브랜드마다 두는 안도 있었다. 이것을 접은 근거는 앞의 측정이다. 인덱스 뒤 브랜드 필터 목록은 DB 안에서 모두 1 ms 아래라서 따로 살려 얻을 것이 적다. 비싼 전체 카탈로그의 페이지는 어느 쓰기에나 바뀌므로 전체의 행은 어차피 모든 쓰기가 올려야 한다.

## revision 행도 잠금의 차례에 넣었다

목록을 바꾸는 쓰기는 여덟이다. 상품 등록, 상품 수정, 재고 수정, 상품 삭제, 주문 확정의 재고 차감, 브랜드 삭제의 연쇄, 브랜드 수정, 좋아요의 누르기와 취소다. 고객은 재고를 품절 여부로만 보므로 두 재고 쓰기는 품절이 바뀔 때만 올린다. 여덟 쓰기가 모두 한 행을 고치므로 이 행은 새로운 잠금이다.

이 행을 3주차의 잠금 순서 맨 끝에 두었다. 주문 → 브랜드 → 상품(id 오름차순) → 포인트 계정 → revision이다. 올리기를 트랜잭션의 마지막 SQL로 보내면, revision을 쥔 트랜잭션은 다른 잠금을 기다리지 않고 commit으로 간다. 아무것도 기다리지 않는 트랜잭션은 교착의 고리에 들 수 없다.

코드의 마지막 줄에 두는 것만으로는 모자랐다. Spring은 `beforeCommit` 훅을 Hibernate가 commit 안에서 flush하기 전에 부른다. 좋아요 취소의 DELETE는 flush에서야 나가고, 그때 처음 좋아요 행을 잠근다. 훅에서 곧바로 upsert를 보내면 revision을 쥔 채 좋아요 행을 기다리게 된다. 그래서 훅은 먼저 flush하고 upsert를 보낸다. 한 트랜잭션에서 여러 번 표시해도 한 번만 올린다. upsert가 마지막 SQL이라는 것은 SQL 로그를 보는 테스트가 쓰기마다 고정한다.

대가도 있다. 좋아요 수를 비정규화하지 않아 좋아요를 상품 행의 잠금에서 떼어 두었는데, 캐시 때문에 좋아요가 결국 revision 행의 잠금을 기다리게 되었다. 다만 revision 행은 upsert에서 commit까지만 쥐므로, 주문 확정이 상품 행을 쥐는 시간보다 짧다. 다른 쓰기가 revision 행을 3초 넘게 쥐면 좋아요는 409 `CONCURRENT_REQUEST`로 끝난다.

## 캐시 전후

miss는 표본마다 캐시를 비우고(비우는 시간은 재지 않는다), hit는 한 번 채운 같은 키를 거듭 읽었다. 단언하는 것은 요청당 SQL(miss 3, hit 1)과 응답이 seed의 기대값과 엄격하게 같다는 것이다. 시간은 이번에도 출력만 한다.

| 요청 | 경로 | 요청당 SQL | 준비·표본 | 지연 p50 |
| --- | --- | --- | --- | --- |
| 브랜드 7 `price_asc` | miss | 3 | 50 · 200 | 4.237 ms |
| 브랜드 7 `price_asc` | hit | 1 | 50 · 200 | 2.408 ms |
| 전체 카탈로그 `likes_desc` | miss | 3 | 10 · 50 | 93.084 ms |
| 전체 카탈로그 `likes_desc` | hit | 1 | 10 · 50 | 2.136 ms |

전체 카탈로그 `likes_desc`는 hit에서 DB 안 91.8 ms의 집계 정렬이 통째로 빠진다. 전체 스위트 안에서 잇달아 돈 세 실행에서도 hit의 p50은 1.979–2.061 ms였다. hit에 남는 일은 revision의 기본 키 조회, Redis GET 한 번, 2.3 KB 남짓의 JSON 역직렬화, 그리고 디스패치와 응답 직렬화다.

브랜드 7은 4.2 → 2.4 ms로 차이가 작다. 인덱스 뒤 그 페이지 쿼리는 DB 안 0.1 ms 남짓이라 캐시가 건너뛸 몫이 적다. 두 처방은 서로 다른 요청을 고친 것이다.

miss의 SQL은 캐시 전의 둘에서 셋이 되었다. revision 읽기와 Redis 왕복 둘(값이 없는 GET, SET)이 더해진다. 캐시 전의 p50(브랜드 7 5.870 ms, 전체 카탈로그 85.210 ms)은 다른 실행에서 쟀으므로 miss와 견주지 않는다.

## Redis나 DB가 멈추면

Redis가 실패하면 DB에서 답한다. 명령은 100 ms, 연결은 1 s에서 끊는다(Lettuce의 기본값은 60 s와 10 s다). 실패한 GET은 miss가 되고, 실패한 SET은 건너뛴다. 둘 다 WARN을 남긴다. Spring의 기본 오류 처리기는 다시 던지므로 삼키는 처리기를 따로 두었다. 캐시 쓰기는 곧바로 보내고 답을 기다리게 했다. 비동기 쓰기에서는 쓰기 오류가 처리기에 닿지 않는다. 같은 이유로 `transactionAware()`는 켜지 않았다. 켜면 쓰기가 commit 뒤로 미뤄지고, 그 예외가 처리기를 거치지 않은 채 이미 commit한 목록 요청을 실패시킨다.

테스트는 자기 전용 Redis 컨테이너를 `docker stop`으로 멈추고 `docker pause`로 걸리게 했다. 두 경우 모두 목록은 2초 안에 DB의 결과로 답하고, 실패한 get과 put을 하나씩 WARN으로 남긴다. Redis가 멈춘 동안 commit한 상품 수정은 캐시 오류 없이 commit하고, 멈춘 동안과 다시 띄운 뒤 모두 새 가격이 보인다. 다시 띄운 Redis에 옛 revision의 값이 남아 있어도 아무도 그 키를 읽지 않는다. 다시 띄운 뒤 첫 읽기가 채우고 다음 읽기가 hit다.

DB가 실패하면 페이지가 캐시돼 있어도 목록은 500 `INTERNAL_ERROR`다. revision 읽기가 캐시를 보기 전의 첫 문장이기 때문이다. 캐시는 DB의 부하를 덜 뿐 DB의 장애를 가리지 않는다.

## 치른 값, 확인하지 않은 것, 다시 볼 조건

치른 값:

- 인덱스가 하나 늘었다. 다만 열이 `brand_id`, `price`, `id`뿐이라 재고 변경과 논리 삭제는 이 인덱스를 건드리지 않는다. 상품 등록과, 가격이 실제로 바뀐 수정만 고친다.
- hit에도 SQL 하나가 남는다. revision의 기본 키 조회다. revision을 Redis에 두면 없앨 수 있지만, 그러면 앞에서 피한 무효화 실패가 돌아온다.
- 어느 쓰기든 모든 목록 키를 무효로 만든다. 다른 브랜드의 키도, 좋아요 하나에도 그렇다. 좋아요가 잦으면 hit가 드물어진다.
- revision이 오른 직후 같은 키를 동시에 읽는 조회들은 저마다 DB를 읽는다. 값이 같아 틀리지는 않지만 비싼 페이지가 동시 요청의 수만큼 다시 계산된다. 쇄도를 막는 장치는 두지 않았다.
- 키를 지우지 않으므로 옛 키가 TTL까지 남는다. 그 메모리는 miss 비율 × TTL × 항목 크기 이하다. 초당 miss 100이면 5분 동안 키 3만 개, 약 79 MB다.
- revision은 뒤로 가면 안 된다. DB를 백업에서 되살리면 목록 캐시의 키를 지워야 한다.
- 목록을 바꾸는 쓰기가 새로 생겼는데 revision을 올리지 않으면, 오류 없이 옛 결과가 남는다. 쓰기마다의 장면 테스트만이 그것을 막는다.

확인하지 않은 것:

- 측정은 개발 기기(Apple M2 Pro)의 Docker에서 했다. MockMvc는 네트워크와 톰캣을 지나지 않는다. 절대값이 아니라 한 실행 안의 비교로만 읽어야 한다.
- revision 행이 초당 몇 건의 쓰기를 받아 내는지는 재지 않았다. 이론상 commit의 지연이 그 상한을 정한다.
- 실제 트래픽에서의 hit 비율과 쇄도의 비용도 재지 않았다.
- 히스토그램이 없을 때 MySQL은 `deleted_at is null`이 행의 10%를 남긴다고 짐작했다. 이 짐작이 계획을 바꾸는지는 보지 않았다.

다시 볼 조건:

- 한 브랜드에서 싼 상품이 많이 삭제되는 경우. 인덱스는 `deleted_at`을 모르므로 21행을 채울 때까지 삭제된 항목도 읽는다.
- 깊은 페이지, 브랜드 없는 가격순, 최신순을 재야 하는 경우. 이번 인덱스는 브랜드를 고른 가격순만 받친다.
- 브랜드 삭제의 잠금 읽기에 정렬 단계가 생겨 연쇄 가드가 실패하는 경우.
- revision 행에서 잠금 대기나 409가 실제로 보이거나, 좋아요가 잦아 hit가 드문 경우. 좋아요를 이 행에서 떼어 내고 좋아요 수의 비정규화를 다시 본다.
- 상품 상세도 캐시하거나, 배치와 스트리머가 상품·브랜드·좋아요를 바꾸기 시작하는 경우.

설계의 전체 기록은 [카탈로그 설계 8절](../design/catalog.md)과 [ADR 0020](../adr/0020-product-list-cache-keyed-by-a-db-revision-locked-last.md)에 있다.
