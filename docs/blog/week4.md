# 브랜드 상품 목록에서 정렬 단계를 인덱스로 없앤 방법과 이유

4주차 과제는 캐시를 붙이기 전에 병목부터 증명하라고 했다. 측정 대상은 이미 있던 조회 하나였다. 브랜드를 골라 가격 낮은순으로 보는 상품 목록의 첫 페이지다. 필터, 정렬, 페이지, 삭제 조건은 그대로 두고 줄여야 했다. 성능 비교를 위해 다른 인덱스를 지워서도 안 됐다.

결론부터 적는다. `(brand_id, price, id DESC)` 인덱스를 기존 `brand_id` 인덱스 옆에 더했다. 실행 계획에서 정렬 단계가 사라졌고, 쿼리가 읽는 행의 수는 브랜드의 크기와 상관없게 되었다. 이 인덱스에서 가장 오래 고민한 부분은 열의 차례가 아니었다. 기존 인덱스를 왜 지우면 안 되는가였다.

## 먼저 잰 것

재현할 수 있는 seed를 Kotlin으로 만들었다. 브랜드는 101개이고 그중 2개는 삭제되었다. 상품은 12,000개이고, 그중 2,000개가 큰 브랜드 101에 몰려 있다. 사용자는 1,000명, 좋아요는 126,955개다. 가격과 브랜드는 과제가 예시로 든 식을 그대로 썼다. 삭제된 상품, 품절 상품, 좋아요가 없는 상품, 동점도 일부러 넣었다. 데이터는 Testcontainers의 MySQL 8.4에 넣고, 넣은 뒤 `ANALYZE TABLE`로 통계를 새로 만들었다.

계획은 직접 적은 SQL로 보지 않았다. 애플리케이션이 실제로 보낸 SQL을 테스트 안에서 잡아 같은 바인드 값으로 `EXPLAIN`했다. Hibernate가 보낸 페이지 쿼리는 다음과 같다(컬럼은 줄였다).

```sql
select … from product p1_0
join brand b1_0 on b1_0.id = p1_0.brand_id and (b1_0.deleted_at is null)
where (p1_0.deleted_at is null) and b1_0.id = ?
order by p1_0.price, p1_0.id desc
limit ?, ?   -- 0, 21: 20개를 보여 주고 1개로 다음 페이지가 있는지 본다
```

기존 스키마에서 MySQL은 `brand_id` 인덱스로 그 브랜드의 상품을 모두 읽었다. 삭제된 상품을 거르고 정렬한 뒤 21행을 잘랐다.

```
-> Limit: 21 row(s)
    -> Sort: p1_0.price, p1_0.id DESC, limit input to 21 row(s) per chunk
        -> Filter: (p1_0.deleted_at is null)
            -> Index lookup on p1_0 using IDX_PRODUCT_ON_BRAND_ID (brand_id=7)   rows=100
```

브랜드 7은 100행을 읽고 0.298 ms가 걸렸다. 브랜드 101은 2,000행을 읽고 1.22 ms가 걸렸다. 브랜드가 커지면 읽고 정렬할 행도 같이 늘어난다. 이것이 이번 병목이다.

## `id DESC`까지 적어야 했던 이유

목록의 차례는 `price ASC, id DESC`다. 같은 가격이면 늦게 등록된 상품이 앞선다. 처음 떠오르는 인덱스는 `(brand_id, price)`인데, 이 인덱스로는 정렬이 사라지지 않는다.

InnoDB의 보조 인덱스는 항목 끝에 기본 키를 붙인다. 그래서 `(brand_id, price)`는 실제로 `(brand_id, price, id)`의 오름차순으로 저장된다. 앞으로 읽으면 `price ASC, id ASC`이고, 뒤로 읽으면 `price DESC, id DESC`다. 어느 쪽으로 읽어도 방향이 섞인 `price ASC, id DESC`는 나오지 않는다. 미리 해 본 탐침에서도 이 인덱스를 두었을 때 정렬이 남았다. [InnoDB 클러스터드·보조 인덱스](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html), [ORDER BY 최적화](https://dev.mysql.com/doc/refman/8.4/en/order-by-optimization.html)

MySQL 8은 인덱스의 열마다 내림차순을 저장할 수 있다. `id DESC`를 명시하면 인덱스의 차례가 목록의 차례와 같아진다. [내림차순 인덱스](https://dev.mysql.com/doc/refman/8.4/en/descending-indexes.html) 엔티티에는 주문 목록 인덱스와 같은 표기로 선언했다.

```kotlin
Index(name = "IDX_PRODUCT_ON_BRAND_ID_AND_PRICE_AND_ID", columnList = "brand_id, price, id DESC")
```

이제 MySQL은 인덱스를 앞에서부터 읽으며 삭제된 상품만 거르고, 21행이 차면 멈춘다.

```
-> Limit: 21 row(s)
    -> Filter: (p1_0.deleted_at is null)
        -> Index lookup on p1_0 using IDX_PRODUCT_ON_BRAND_ID_AND_PRICE_AND_ID (brand_id=7)   actual rows=22
```

22행을 읽은 것은 앞쪽 22개 가운데 하나가 삭제된 상품이었기 때문이다. 브랜드 101도 똑같이 22행을 읽었다. 읽는 행의 수가 브랜드의 상품 수가 아니라 페이지 크기를 따르게 되었다.

## 기존 인덱스를 지우지 않은 이유: 잠금의 차례

새 인덱스는 `brand_id`로 시작하므로 기존 `brand_id` 단독 인덱스는 그 앞부분처럼 보인다. 중복 인덱스처럼 보여서 지우고 싶어진다. 하지만 지우면 3주차에 세운 규칙이 깨진다.

3주차에 브랜드를 삭제하면 그 브랜드의 상품을 `FOR UPDATE`로 잠그고 함께 삭제하게 했다. 교착을 피하려고 모든 경로가 상품을 id 오름차순으로 잠근다는 규칙도 두었다. 그런데 InnoDB의 잠금 읽기는 `ORDER BY`의 차례가 아니라 **훑는 인덱스의 차례**로 행을 잠근다. 단독 인덱스는 끝에 붙은 기본 키 때문에 id 차례로 읽히고, 그래서 id 차례로 잠긴다. [잠금 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

단독 인덱스를 지우면 두 가지가 바뀐다.

- MySQL은 외래 키에 인덱스를 요구한다. 단독 인덱스가 없어지면 `brand_id`로 시작하는 복합 인덱스가 외래 키를 받친다. [외래 키 제약](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)
- 브랜드 삭제의 잠금 읽기도 복합 인덱스를 따라 읽는다. 그러면 상품이 가격 차례로 잠긴다.

`(brand_id, deleted_at, price, id DESC)`도 검토했다. 삭제 조건까지 인덱스로 걸러 가격순에서는 정확히 21행만 읽는다. 하지만 탐침에서 옵티마이저는 브랜드 삭제의 잠금 읽기에 이 인덱스를 골랐다. `performance_schema.data_locks`를 보니 가장 싼 상품부터 잠겼다. 계획에는 `Sort: p1_0.id`가 붙어 있었지만, 이 정렬은 돌려줄 행의 차례만 바꾼다. 이미 걸린 잠금의 차례는 바꾸지 못한다. 그 밖에도 브랜드의 좋아요 많은순이 이 인덱스로 옮겨 가 0.54 ms에서 0.90 ms로 느려졌다. 논리 삭제는 `deleted_at`을 바꾸므로 삭제할 때마다 인덱스도 고쳐야 했다.

그래서 단독 인덱스를 남기고, 그 이유를 엔티티의 KDoc에 적었다. 말로만 남기지 않고 테스트로도 지킨다. 큰 seed 위에서 실제 브랜드 삭제를 롤백할 트랜잭션 안에서 실행해 잠금 읽기 SQL을 잡는다. 그 계획에 정렬 단계가 없는지 단언한다. 정렬 없이 `ORDER BY id`에 답하는 계획은 id 차례로 읽고, 그 차례로 잠근다. `(brand_id, deleted_at, price, id DESC)`를 더해 보면 이 테스트는 `Sort: p1_0.id`를 내며 실패했다.

## 전후를 한 실행 안에서 비교하기

인덱스를 지웠다가 다시 만들지 않았다. 인덱스를 `INVISIBLE`로 바꾼 상태를 "전", `VISIBLE`로 되돌린 상태를 "후"로 두었다. 옵티마이저는 숨긴 인덱스를 보지 않지만, 쓰기는 계속 그 인덱스를 고친다. 그래서 같은 seed와 같은 통계 위에서 인덱스 하나만 달라진다. [보이지 않는 인덱스](https://dev.mysql.com/doc/refman/8.4/en/invisible-indexes.html) 이 DDL은 열린 트랜잭션을 암묵적으로 커밋한다. 그래서 테스트는 롤백 트랜잭션 밖에서 돈다. 테스트가 실패해도 `finally`에서 인덱스를 다시 보이게 한다. 스키마는 다음 테스트 클래스에도 남기 때문이다.

빨라졌다는 것만으로는 개선이라고 보지 않았다. 두 상태의 응답 본문이 seed에서 따로 계산한 기대값과 엄격하게 같아야 하고, 서로 글자까지 같아야 한다. 첫 페이지 전체가 1,000원 한 가격인 브랜드 101에서는 동점 규칙만이 차례를 정한다. 인덱스의 `id DESC`가 그 규칙을 그대로 지켰다.

| 요청 | 상태 | 읽은 행 | 정렬 | DB 안 시간 | 지연 p50 (준비 50, 표본 200) |
| --- | --- | --- | --- | --- | --- |
| 브랜드 7 | 전 | 100 | 있음 | 0.298 ms | 6.724 ms |
| 브랜드 7 | 후 | 22 | 없음 | 0.073 ms | 5.870 ms |
| 브랜드 101 | 전 | 2,000 | 있음 | 1.22 ms | 5.369 ms |
| 브랜드 101 | 후 | 22 | 없음 | 0.101 ms | 3.380 ms |

요청 하나의 지연은 DB 안 시간만큼 줄지 않았다. MockMvc로 잰 지연에는 디스패치, 검증, JSON 직렬화, 두 SQL의 왕복이 모두 들어 있다. 페이지 쿼리는 그중 작은 몫이다. 그래서 차이는 DB 안에서 1 ms 넘게 줄어든 브랜드 101에서만 분명하게 보였다. 지연의 꼬리는 실행마다 크게 흔들렸다. 브랜드 7 "후"의 p99가 한 실행에서는 33.6 ms, 다른 실행에서는 5.6 ms였다. 그래서 시간은 출력만 하고 단언하지 않는다. 이 인덱스의 진짜 효과는 읽는 행이 브랜드의 크기를 따르지 않게 된 것이다.

## 치른 값과 다시 볼 조건

인덱스가 하나 늘었으니 쓰기 비용도 늘었다. 다만 그 범위는 좁다. 새 인덱스의 열은 `brand_id`, `price`, `id`뿐이다. 재고 변경(주문 확정의 차감 포함)과 논리 삭제는 이 열을 바꾸지 않으므로 인덱스를 건드리지 않는다. 상품 등록과, 가격이 실제로 바뀐 수정만 인덱스를 고친다.

다음과 같은 일이 생기면 이 선택을 다시 본다.

- 한 브랜드에서 싼 상품이 많이 삭제되는 경우. 인덱스는 `deleted_at`을 모르므로 21행을 채울 때까지 삭제된 항목도 읽는다.
- 깊은 페이지, 브랜드 없는 가격순, 최신순을 재야 하는 경우. 이번 인덱스는 브랜드를 고른 가격순 첫 페이지만 받친다.
- 연쇄 가드가 실패하는 경우. 통계가 바뀌어 옵티마이저가 브랜드 삭제에 복합 인덱스를 고르면 잠금의 차례가 다시 문제가 된다.

같은 측정에서 해결하지 못한 것도 하나 보였다. 브랜드 없이 전체 카탈로그를 좋아요 많은순으로 보는 첫 페이지다. 이 요청은 DB 안에서 90 ms 남짓 걸린다. 삭제되지 않은 상품 11,444개의 좋아요 123,255행을 조인하고, 센 수로 정렬한 뒤에야 페이지를 자를 수 있다. 집계한 값으로 정렬하므로 인덱스로는 정렬을 없앨 수 없다. 좋아요 수를 상품에 저장하면 해결되지만, 누를 때와 취소할 때마다 상품 행을 고치는 쓰기 경로가 생긴다. 이번에는 좋아요 수를 계속 관계에서 세기로 했다. 이 측정값은 다음 단계인 캐시 설계에서 어떤 조회를 캐시할지 고르는 근거가 된다.
