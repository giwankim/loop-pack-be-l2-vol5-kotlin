# 결제를 시작하는 확정은 `Idempotency-Key`를 요구하고, 같은 키의 재요청에는 저장된 상태로 답한다

[ADR 0005](./0005-no-request-idempotency-until-a-retrying-caller.md)는 재시도하는 호출자가 생기거나 과제가 요구할 때 요청 멱등성을 다시 열기로 했다. 2단계에서 둘 다 왔다. 과제는 확정이 시도 키(`paymentAttemptKey`)를 받으라고 하고, 202를 잃은 고객은 결제를 하나 더 만들지 않고 다시 물을 수 있어야 한다. 확정이 PG를 부르므로([ADR 0024](./0024-confirm-calls-the-pg-between-two-transactions.md)) 같은 요청을 두 번 처리하면 PG 거래가 둘이 될 수 있다.

1. **확정은 `Idempotency-Key` 헤더를 요구한다.** 없으면 400이다. 본문은 카드(`cardType`, `cardNo`)뿐이고, 금액은 저장된 주문에서 정한다. 과제의 `paymentAttemptKey`를 본문 대신 IETF 초안(`draft-ietf-httpapi-idempotency-key-header`)과 Stripe, Toss가 쓰는 헤더로 받는다.
2. **키는 그대로 비교하고, 모든 사용자에 걸쳐 유일하다.**
   - 1자에서 64자까지의 공백 없는 보이는 ASCII다. 웹 경계와 `Payment`의 생성이 둘 다 검사한다.
   - 열은 `utf8mb4_bin`이라 대소문자와 끝 공백을 가른다.
   - 유일성은 `UK_PAYMENT_ON_IDEMPOTENCY_KEY`가 지킨다. 결제에는 사용자 식별자가 없어, 사용자마다 유일하게 하려면 결제가 주문을 건너야 한다.
3. **재요청에는 업무 기록, 곧 결제와 주문으로 답한다([ADR 0004](./0004-replay-success-from-business-records.md)).** 응답을 따로 저장하지 않는다.

   | 요청 | 답 |
   | --- | --- |
   | 같은 키, 같은 주문 | PG를 부르지도 조회하지도 않고 저장된 상태로 답한다. 결제 중인 주문이면 202와 `Location: /api/v1/orders/{orderId}`, 확정됐거나 결제에 실패했으면 200이다. 카드는 저장하지 않으므로 견주지 않는다. |
   | 결제가 있는 주문에 다른 키 | 409 `IDEMPOTENCY_KEY_MISMATCH`. 바뀌는 것이 없다. |
   | 다른 주문이 이미 쓴 키 | 409 `IDEMPOTENCY_KEY_IN_USE`. 바뀌는 것이 없다. 두 TX A가 겨루면 진 쪽의 결제 삽입이 유일 제약에 걸려 그 TX A가 예약과 함께 되돌아간다. |
   | 포인트로 확정된 이전 주문 | 409 `ORDER_ALREADY_CONFIRMED`(과제 3절). |
   | PG를 부르기 전의 거절 | 기존 오류. 결제가 생기지 않았으므로 키도 쓰이지 않았고, 같은 키로 다시 확정할 수 있다. |

   - 재요청은 첫 응답이 아니라 지금 저장된 상태를 돌려준다. 첫 요청이 202였어도 그 뒤 TX B가 끝났으면 200이다. PG의 답을 새로 알려면 대사 API를 부른다.
   - 대사 API도 같은 202/200을 쓴다. 결제를 시작하지 않은 주문에는 409 `PAYMENT_NOT_STARTED`다.

## 고르지 않은 것

- **본문의 `paymentAttemptKey`.** 과제의 식별자는 강제가 아니다. 헤더가 널리 쓰는 모양이고, 본문에 카드만 남아 결제의 입력과 재요청의 열쇠가 섞이지 않는다.
- **첫 응답을 저장해 그대로 재생한다(Stripe).** 응답 표와 그 만료가 더 든다. 고객이 같은 키로 다시 묻는 까닭은 결과를 알고 싶어서이므로, 지금 상태가 더 쓸모 있다.
- **사용자마다 유일한 키.** 규칙 2의 까닭으로 결제가 주문을 건너거나 사용자 식별자를 더 가져야 한다. 무작위 키라면 사용자끼리 부딪힐 일이 없다.
- **같은 키, 같은 주문에 카드가 다르면 거절한다.** 카드를 저장하지 않으므로(과제) 견줄 것이 없다.

## 대가

- 헤더를 보내지 않는 클라이언트는 400을 받는다. ADR 0005가 말한 대로 필수 헤더는 기존 계약을 바꾼다.
- 남의 주문이 쓴 키에 409가 나가므로 그 키가 쓰였다는 것이 드러난다. 무작위로 만든 키에서는 뜻이 없다.
- 키는 사라지지 않는다. 결제 행이 남는 동안 같은 키를 다른 주문에 다시 쓸 수 없다.

## 다시 볼 조건

- 충전이나 주문 생성에도 재시도하는 호출자가 생기면 그때 키를 들인다. 둘은 ADR 0005 그대로다.
- 실패한 뒤 다시 결제하는 것을 허용하면 키는 결제가 아니라 시도마다 하나가 된다(ADR 0021의 다시 볼 조건).

## 바꾸는 결정

확정에 한해 ADR 0005를 대체한다. 충전과 주문 생성은 그대로다. ADR 0005의 두 번째 줄(확정 재요청의 409)과 [ADR 0019](./0019-order-and-point-account-rows-locked-on-first-read.md)의 "새 요청 키를 들이지 않는다"가 바뀐다. 두 ADR의 날짜 메모는 구현하는 작업에서 단다. `CONTEXT.md`의 멱등 키가 이 ADR을 따른다.
