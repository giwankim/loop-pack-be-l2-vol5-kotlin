# 누락 복구는 지정한 주문의 저장된 확정 사실에서 행을 더하고, 추측하지 않고 거절한다

7주차 과제 5절은 6주차의 누락 상태를 새 격리 실행에서 재현하고 같은 실행 안에서 복구하라고 한다. 대상 두 주문의 저장된 확정 사실에서 기존 eventId·confirmedAt·품목 그대로 아웃박스가 없을 때만 한 행씩 더하고, 이미 있으면 내용이 같은지 확인하며, 사실이 모자라거나 어긋나면 추측하지 않고 오류를 드러내라고 한다. 이전 POINT 주문 전체를 자동 소급하지 않는다. 복구 중에는 PG를 더 부르지 않고 주문을 다시 확정하지 않으며 예약을 더 소비하지 않는다. 준비는 "보존한 W6 테스트 구성 또는 W6 revision 실행물"로 6주차의 after-commit 직접 발행 경로를 실행한다.

이 저장소에서는 이 일을 **누락 복구**라 부른다([`CONTEXT.md`](../../CONTEXT.md)). [ADR 0034](./0034-order-confirmed-is-left-in-an-outbox-row-by-tx-b.md)가 행을 남기는 곳을 TX B 하나로 정했으므로, 이 ADR은 그 밖에서 행이 생기는 유일한 길이다.

1. **누락 복구는 운영 코드다.** 애플리케이션 서비스가 주문을 읽어 `OrderConfirmedEvent.from(order)`와 `OrderEventSerializer`로 행을 만든다. TX B와 같은 행을 만들어야 하므로 `OrderPaymentSagaSteps.leaveInOutbox`의 행 만들기를 뽑아 둘이 나눠 쓴다(주문 아웃박스 설계 10절이 예고한 추출이다). 이벤트 ID는 주문에서 유도하므로(`order-confirmed:v1:<orderId>`) 6주차에 나갔던 것과 같다.
2. **대상은 사람이 지정한 주문뿐이다.** "확정됐는데 행이 없는 주문"을 찾지 않는다. 진입점은 한 클래스의 `ApplicationRunner`이고 `order-events.recovery.order-ids`가 비어 있으면(기본) 아무것도 하지 않는다. 엔드포인트는 없다. 앱을 그 값으로 다시 띄우면 행이 더해지고 중계가 보낸다.
3. **주문마다 결과는 넷 중 하나다.**

   | 주문과 행 | 결과 |
   | --- | --- |
   | 주문이 없다, `confirmedAt`이 없다, `paymentMethod`가 `PG`가 아니다 | 거절 |
   | 행이 없다 | `PENDING`으로 더하고 지금 차례로 둔다 |
   | 행이 있고 `event_id`, `order_id`, `event_type`, `schema_version`, `message_key`, `payload`(문자열 그대로)가 모두 같다 | 아무것도 하지 않는다. 상태가 `PUBLISHED`나 `BLOCKED`여도 같다 |
   | 행이 있고 하나라도 다르다 | 거절. 이벤트 ID와 다른 열 이름을 드러내고 payload는 적지 않는다 |

   주문마다 INFO 한 줄로 결과를 남긴다. 주문마다 자기 트랜잭션이고 첫 거절에서 멈춘다. 앞서 더한 행은 남지만 다시 돌리면 아무것도 하지 않으므로 안전하다. 거절은 시작을 실패시켜 눈에 띈다.
4. **잠그지 않는다.** 동시에 두 번 돌면 유일한 `event_id`에서 하나가 실패하고, 다시 돌리면 아무것도 하지 않는다. TX B와는 겹치지 않는다. 대상이 이미 확정된 주문이기 때문이다. (2026-11-06, [issue 217](https://github.com/giwankim/loop-pack-be-l2-vol5-kotlin/issues/217): 진 쪽이 늘 실패하지는 않는다. 먼저 커밋된 행을 찾으면 같은 행이라 `ALREADY_PRESENT`로 끝난다. 어느 쪽이든 행은 하나다. [issue 212](https://github.com/giwankim/loop-pack-be-l2-vol5-kotlin/issues/212)의 장면이 두 갈래를 모두 받아들이고, 처음 돌린 때는 충돌 쪽을 탔다. 주문 아웃박스 설계 14.2절이다.)
5. **5절의 준비는 보존한 W6 테스트 구성이다. W6 revision의 jar를 띄우지 않는다.** 6주차와 지금의 확정 경로는 TX B의 한 곳(`publish` 대신 `leaveInOutbox`)만 다르다. 테스트는 `OrderEventOutboxRepository`의 spy로 `save`가 행을 쓰지 않게 하고 커밋 뒤 보내기를 건다. A는 보내지 않고, B는 그 행을 지금의 `KafkaOrderEventPublisher`로 보낸다. record의 bytes는 6주차와 같다고 못 박혀 있다. 그다음 spy 없는 둘째 컨텍스트가 같은 컨테이너에서 복구 ID로 뜨고, 셋째가 같은 ID로 다시 뜬다. 행을 지우거나 `SUCCESS`를 넣지 않는다.

## 고르지 않은 것

- **W6 revision(`eba8534`)의 bootJar를 자식 프로세스로 띄운다.** 실제 6주차 코드이고, 닿지 않는 broker 주소로 확정한 뒤 `kill -9`하면 진짜 프로세스 정지다([측정 기록](../research/week7-outbox-recovery-probe.md): `CONFIRMED`, record 0). 그러나 옛 판을 꺼내 빌드하는 Gradle 작업과 따로 도는 앱이 하나 는다. 그 무게를 들이지 않기로 했다. W6 DB에 표를 더하는 단계(`ddl-auto=update`)는 같은 측정에 있다.
- **테스트 전용 코드로만 복구한다.** 생각은 보여 주지만 실제 누락을 닫을 길이 없다.
- **문서의 SQL로 행을 더한다.** MySQL의 `JSON_OBJECT`는 키의 차례를 지키지 않아 payload가 직렬화기의 것과 달라진다.
- **확정됐는데 행이 없는 주문을 모두 찾아 더한다.** 과제가 막는 자동 소급이고, 포인트로 확정된 이전 주문을 거르는 규칙이 하나 더 필요하다.
- **로컬 전용 엔드포인트.** 과제도 사용자도 원하지 않는다.

## 대가

- 5절의 준비에서 도는 6주차 코드는 실제 판이 아니라 지금의 TX B와 테스트의 보내기다. A의 멈춤은 보내지 않은 것이지 프로세스 강제 종료가 아니다.
- 표가 처음부터 있으므로 W6 DB에 아웃박스 표를 더하는 단계는 테스트되지 않는다. 운영에는 마이그레이션 도구가 없다(주문 아웃박스 설계 9절).
- 진입점을 쓰려면 앱을 다시 띄워야 한다.

## 다시 볼 조건

- 누락이 지정할 수 없을 만큼 많아지면 찾는 쪽을 본다.
- 이벤트 종류나 판이 늘면 "같은 행"의 비교를 다시 본다.
