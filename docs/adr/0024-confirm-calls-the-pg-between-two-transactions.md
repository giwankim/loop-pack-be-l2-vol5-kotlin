# 주문 확정은 PG 호출을 두 트랜잭션 사이에 두고, 앞 트랜잭션의 커밋을 발송 기록으로 삼는다

[ADR 0003](./0003-confirm-order-in-one-transaction.md)은 주문, 재고, 포인트를 한 트랜잭션에서 바꿨다. 5주차 2단계는 포인트 대신 로컬 테스트 PG로 결제한다. 과제는 PG 호출 동안 DB 트랜잭션과 재고 잠금을 쥐지 말고, 발송 권한을 가진 쪽만 생성을 보내며, 발송 시작을 저장한 뒤에는 생성을 다시 보내지 말라고 한다. 테스트 PG는 같은 PG 주문 번호의 생성을 하나로 합친다고 약속하지 않는다. 취소 API도, "이 PG 주문 번호에는 앞으로 PG 거래가 생기지 않는다"는 약속도 없다. 조회가 0건이어도 PG 거래가 없다는 증거가 아니다([ADR 0022](./0022-only-the-pre-create-rejection-proves-no-pg-transaction.md) 규칙 3).

1. **확정은 TX A, PG 호출, TX B 세 단계다.**
   - TX A는 주문을 잠가 확정 전인지 본 뒤 재고를 예약하고([ADR 0026](./0026-stock-reservation-is-the-pending-orders-line-items.md)), 주문을 결제 중인 주문으로 바꿔 결제수단 PG를 적고, 결제를 결과 미확인으로 만들어 커밋한다.
   - PG 호출은 트랜잭션도 잠금도 쥐지 않고 생성을 한 번 보낸다.
   - TX B는 주문을 다시 잠그고 PG의 답을 결제에 반영한다. 결제가 성공으로 끝나면 주문을 확정하고 예약을 소비한다. 실패로 끝나면 주문을 결제에 실패한 주문으로 바꾸고 예약을 한 번 돌려준다. 처리 중이면 주문은 그대로다.
   - PG를 부르기 전의 거절(잘못된 카드, 재고 부족, 주문할 수 없는 상품)은 TX A를 시작하기 전이나 TX A 안에서 난다. 주문은 확정 전 그대로이고 PG는 한 번도 불리지 않는다. 카드는 확정 요청이 포트와 같은 제약으로 먼저 검사한다. 포트의 검사가 TX A 뒤에 처음 실패하면, 보내지 않을 결제가 결과 미확인으로 남아 예약을 영영 쥔다. (2026-10-22: 구현하며 이 거절을 하나 더 찾았다. PG는 금액을 64비트 정수로 받는데 주문 합계는 그보다 클 수 있다. 결제의 금액 열은 `DECIMAL(65,0)`이므로, 결제를 만드는 결제 슬라이스의 포트가 TX A 안에서 9,223,372,036,854,775,807원을 넘는 금액을 400으로 거절한다. TX A 뒤에 PG 요청을 만들다 실패하면 위와 같이 예약을 영영 쥔다.)
2. **TX A의 커밋이 발송 기록이다.** 결과 미확인 결제를 커밋한 요청만 생성을 보낸다. 같은 주문의 다른 확정은 주문 잠금에서 기다린 뒤, 이미 결제가 있는 주문을 본다([ADR 0025](./0025-confirm-requires-an-idempotency-key-and-replays-stored-state.md)).
   - "보냈다"를 따로 적지 않는다. POST 뒤에 적으려면 트랜잭션이 하나 더 들고, POST와 그 기록 사이에 프로세스가 멈추면 보낸 요청이 보내지 않은 것으로 남는다.
   - 커밋 뒤 POST 전에 멈춘 것과 응답을 잃은 것은 DB로 가를 수 없으므로 같게 다룬다. 둘 다 조회로만 결과를 알고, 다시 보내지 않는다.
3. **생성은 다시 보내지 않는다.** 같은 멱등 키의 재요청, 재시작, 대사, 3단계의 알림과 재시도 어느 것도 생성을 부르지 않는다.
4. **결과 미확인과 처리 중에는 기한이 없다.** 예약은 대사가 끝난 결과를 찾을 때까지 남는다. 시간 초과, 재시작, 0건 조회가 예약을 돌려주지 않는다(과제 체크리스트).
5. **TX B는 다시 해도 된다.** TX B가 DB 오류로 되돌아가면 결제는 결과 미확인이나 처리 중으로 남고, 대사 API가 같은 PG 거래를 다시 조회해 같은 경계로 반영한다(과제 장면 7). 대사의 반영도 주문을 먼저 잠그므로 확정의 TX B와 겹쳐도 한 번만 확정하거나 돌려준다. 끝난 결제는 같은 답에 `Unchanged`다([ADR 0021](./0021-payment-is-its-own-aggregate-and-slice.md) 규칙 2).

## 고르지 않은 것

- **PG 호출을 확정의 트랜잭션 안에 둔다(ADR 0003 그대로).** 과제가 금한다. PG가 늦는 동안 주문과 상품의 잠금을 쥐고, 결과 미확인의 예외가 트랜잭션을 되돌려 결제의 기록까지 사라진다([ADR 0023](./0023-pg-port-returns-transactions-and-throws-the-rest.md) 규칙 4).
- **발송 직전이나 직후를 따로 표시한다(`SENDING`).** 규칙 2의 까닭으로 사실대로 적을 수 없다. 주문에 상태를 더 잘게 두지 않는 까닭도 같다. 결과 미확인과 처리 중의 차이는 결제가 가진다.
- **예약에 기한을 두고, 지나면 돌려준다.** 조사한 상거래 시스템의 예약은 모두 기한이 있다([조사](../research/stock-reservation-with-payments.md)). 그 시스템들은 늦게 온 성공을 자동 취소나 환불로 되돌릴 길을 가진다. 테스트 PG에는 그 길이 없어, 돌려준 뒤에 성공이 오면 재고 없이 돈을 받은 주문이 된다.
- **보내지 않은 것이 확실하면 다시 보낸다.** DB로는 확실히 알 수 없다(규칙 2).

## 대가

- 커밋 뒤 POST 전에 멈추거나 조회가 계속 0건이면, 결제는 결과 미확인으로, 재고는 예약된 채로 남는다. 그런 결제를 찾는 지표나 화면은 없다. 알려진 한계로 PR에 적는다.
- 확정 한 번이 트랜잭션 둘과 HTTP 호출 하나다. 고객은 결과 대신 202를 받을 수 있다.
- "확정된 주문에는 성공한 결제가 있다"를 TX B의 응용 서비스가 지킨다(ADR 0021의 대가와 같다).

## 다시 볼 조건

- PG가 같은 PG 주문 번호의 생성을 하나로 합치거나, 어떤 시점 뒤로 PG 거래가 생기지 않는다고 약속하거나, 취소 API를 주면 기한과 다시 보내기를 다시 견준다. 기한을 두면 [ADR 0026](./0026-stock-reservation-is-the-pending-orders-line-items.md)도 다시 연다.
- 결과 미확인으로 오래 남은 결제를 사람이 다뤄야 하면, 그 나이를 재는 지표와 손으로 끝내는 절차를 둔다.

## 바꾸는 결정

ADR 0003을 대체한다. [ADR 0019](./0019-order-and-point-account-rows-locked-on-first-read.md)의 다시 볼 조건("결제가 외부 연동으로 바뀌면")이 왔고, 확정의 잠금 차례는 [ADR 0028](./0028-order-slice-orchestrates-the-payment.md) 규칙 4가 정한다. ADR 0003의 대체 표시와 ADR 0019의 날짜 메모는 구현하는 작업에서 원문을 두고 단다. `CONTEXT.md`의 주문을 확정하다, 결제 중인 주문, 결제에 실패한 주문, 재고 예약이 이 ADR을 따른다.
