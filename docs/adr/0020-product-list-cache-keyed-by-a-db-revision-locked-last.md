# 상품 목록 캐시는 DB의 단일 revision 행으로 무효화하고, revision 행은 잠금 순서의 마지막에 둔다

4주차 과제 3절은 공통 조회 한 경로에 Redis cache-aside를 붙이라고 한다. 고른 경로는 고객 상품 목록 `GET /api/v1/products`이고, 필터·정렬·페이지·크기의 모든 조합을 캐시한다. 응답에 사용자별 필드는 없다([카탈로그 설계 8.1](../design/catalog.md)). 비싼 것은 전체 카탈로그 `likes_desc`의 집계 정렬이다(DB 안 91.8 ms, 8.4). 과제가 지키라는 계약은 이렇다. 장애와 동시 채움이 없으면, 정상 변경이 끝난 뒤 시작한 순차 조회는 바뀐 결과를 돌려준다. 되돌린 변경의 결과는 게시하지 않는다. 삭제된 상품을 보이지 않는 것은 표시 신선도로 느슨하게 할 대상이 아니다. "`@Transactional` + 삭제"나 TTL이 모든 경쟁과 장애에서 최신성을 보장한다고 주장하지 않는다. 시험할 장면에는 commit 뒤의 무효화 실패와, 먼저 시작한 조회의 늦은 채움이 들어 있다.

목록의 응답을 바꾸는 쓰기는 여덟이다. 상품 등록, 상품 수정, 재고 수정, 상품 삭제, 주문 확정의 재고 차감, 브랜드 삭제의 연쇄, 브랜드 수정, 좋아요의 누르기와 취소다. 좋아요 수는 관계에서 세므로(`CONTEXT.md` 좋아요 수) 좋아요도 목록을 바꾼다. 고객은 재고를 품절 여부로만 보므로, 두 재고 쓰기는 품절이 바뀔 때만 목록을 바꾼다.

1. **무효화는 DB의 revision 행 하나가 맡는다.** 상품 목록의 revision은 카탈로그 전체에 하나다. 여덟 쓰기는 자기 트랜잭션 안에서 `insert … on duplicate key update revision = revision + 1` 한 문장으로 그것을 올린다.
   - 더하기는 그 문장 안에서 한다. Kotlin에서 읽고 하나 더해 쓰지 않는다. 그러려면 잠금 읽기가 하나 더 들고, 뜨거운 행을 더 오래 쥔다.
   - 올리기는 쓰기와 같은 트랜잭션에서 한다. `REQUIRES_NEW`나 commit 뒤의 훅으로 옮기지 않는다. 올리기가 실패하면 쓰기도 되돌려지고, 되돌린 쓰기는 revision도 올리지 않는다.
   - 관리자의 재고 수정과 확정의 차감은 품절이 바뀔 때만 올린다. 두 쓰기는 상품 행을 `FOR UPDATE`로 쥔 채([ADR 0018](./0018-pessimistic-row-locks-in-one-global-order.md)) 바뀌기 전과 뒤를 견주므로, 그 판단에 잠금을 더하지 않는다. 좋아요의 누르기와 취소는 관계가 이미 그 상태여도 올린다. 그것을 가려내는 분기는 값어치가 없다.
   - 행이 없으면 revision은 0이다. upsert가 행을 만들므로, 표를 비운 뒤의 올리기가 0행을 고치고 조용히 지나가는 일이 없다.
   - revision 행은 `BaseEntity`를 상속하지 않는 JPA 엔티티다. 생성되는 식별자, 생성·수정·삭제 시각, 논리 삭제가 카운터 하나에는 맞지 않으므로 [ADR 0016](./0016-every-entity-extends-base-entity-and-roots-soft-delete.md)의 예외로 둔다. 표는 다른 표처럼 Hibernate가 만들고, 테스트의 `DatabaseCleanUp`이 함께 비운다. 올리기는 엔티티를 읽어 고치지 않고 위의 upsert 한 문장으로 한다.
2. **고객 목록은 revision을 트랜잭션의 첫 문장으로 읽는다.** 잠그지 않는 일반 `SELECT`다. REPEATABLE READ의 스냅샷이 이 문장에서 정해지므로, 뒤따르는 페이지 쿼리와 좋아요 수 조회는 읽은 revision과 같은 상태를 본다. 키는 revision과 필터·정렬·페이지·크기를 품는다. hit이면 SQL은 revision 하나다. miss면 같은 스냅샷에서 읽은 페이지를 그 키에 만료를 함께 단 `SET` 한 번으로 넣는다.
   - 캐시는 Query Service의 읽기 전용 트랜잭션 안에서 다룬다. `@Cacheable`의 키 생성기가 revision을 읽으므로, `@EnableTransactionManagement`의 order를 캐시보다 앞에 두어 트랜잭션 advisor가 캐시 advisor를 감싸게 한다. 키 생성기는 트랜잭션이 없으면 실패한다. 페이지를 먼저 읽고 revision을 나중에 읽으면, 그 사이 commit한 변경 전의 페이지가 새 revision의 키에 들어간다.
   - 캐시 advisor가 바깥이어도 지금은 revision을 페이지보다 먼저 읽는다. Spring이 조회 때 만든 키를 넣을 때 다시 쓰기 때문이다(6.1.2부터). 그러나 그러면 정확성이 그 구현에 기댄다. 트랜잭션이 바깥이면 키를 다시 만들어도 같은 스냅샷에서 같은 revision을 읽는다.
   - `FOR SHARE`로 읽지 않는다. commit하지 않은 쓰기 뒤에 줄을 서고, 스냅샷이 아니라 가장 최근에 commit된 값을 읽는다.
   - revision 자체를 Redis에 캐시하지 않는다(과제). 그러면 아래 고르지 않은 것의 세대 번호가 가진 실패가 돌아온다.
3. **revision 행은 잠금 순서의 마지막이다.** 순서는 주문 → 브랜드 → 상품(id 오름차순) → 포인트 계정 → 상품 목록 revision이다.

   | 경로 | 잠그는 차례 |
   | --- | --- |
   | 주문 확정 | 주문 → 상품 → 포인트 계정 → revision(품절이 바뀌면) |
   | 충전 | 포인트 계정 |
   | 브랜드 삭제 | 브랜드 → 상품 → revision |
   | 브랜드 수정 | 브랜드 → revision |
   | 상품 등록 | 브랜드(공유 잠금) → 새 상품 행 → revision |
   | 관리자의 상품 수정·삭제 | 상품 → revision |
   | 관리자의 재고 수정 | 상품 → revision(품절이 바뀌면) |
   | 좋아요 누르기 | 새 좋아요 행 → revision |
   | 좋아요 취소 | 좋아요 행 → revision |

   - 올리기는 트랜잭션의 마지막 SQL이고, 다른 변경을 flush한 뒤에 나간다. 그래서 revision을 쥔 트랜잭션은 다른 잠금을 기다리지 않고 commit으로 간다. 기다리지 않는 트랜잭션은 교착의 고리에 들 수 없다.
   - 코드의 마지막 줄이라는 것만으로는 모자라다. [ADR 0018](./0018-pessimistic-row-locks-in-one-global-order.md)과 [ADR 0019](./0019-order-and-point-account-rows-locked-on-first-read.md)의 규칙 3은 "commit의 flush가 새 잠금을 얻지 않는다"에 기댄다. 그것은 처음 읽을 때 잠그는 브랜드, 상품, 주문, 포인트 계정 행의 이야기다. 좋아요 행은 잠그지 않고 읽으므로, 취소의 DELETE는 flush에서 처음 그 행을 잠근다. 올리기가 flush보다 먼저 나가면 revision을 쥔 채 좋아요 행을 기다린다. 누르기의 INSERT는 식별자가 `IDENTITY`라서 `save`에서 곧바로 나간다. 외래 키 검사가 상품 행에 거는 공유 잠금도 그때 걸리므로 revision보다 앞선다.
   - flush 뒤에 보내면 뜨거운 행을 쥐는 시간도 짧아진다. 브랜드 삭제의 연쇄가 UPDATE를 50개씩 묶어 보내는 동안([ADR 0018](./0018-pessimistic-row-locks-in-one-global-order.md) 규칙 9) revision을 쥐지 않는다.
   - 문장의 차례는 SQL 로그(`captureSql`)를 보는 테스트가 고정한다.
4. **Redis는 쓰기 경로에 없다.** 쓰기는 Redis에 아무것도 보내지 않는다. Redis가 멈춰도 쓰기는 성공하고, commit 뒤에 실패할 무효화 호출이 없다. 키는 지우지 않는다. revision이 오르면 옛 키는 아무도 읽지 않게 된다.
   - 늦은 채움은 자기가 읽은 옛 revision의 키에 쓴다. 변경의 commit 뒤에 시작한 조회는 새 revision의 키를 읽으므로 그것을 보지 않는다.
   - commit하지 않은 revision은 다른 트랜잭션에 보이지 않는다. 그래서 되돌린 쓰기의 revision으로 채워지는 키가 없다.
   - 한 키의 값은 한 스냅샷의 결과다. 같은 키를 동시에 채우는 조회들은 같은 값을 쓰므로 Lua, `MULTI`, 채우기의 잠금이 필요 없다. Redis replica의 지연도 miss를 늘릴 뿐 옛 값을 돌려주지 않는다.
5. **TTL은 옛 키를 치울 뿐이다.** 신선도는 TTL에 기대지 않는다. TTL을 표시 데이터의 시간 상한으로 내세우지 않는다.

## 고르지 않은 것

- **TTL만 둔다.** 변경 뒤의 순차 조회가 TTL이 끝날 때까지 옛 결과를 받고, 삭제된 상품도 그동안 보인다. 느슨하게 할 수 없는 계약이다.
- **트랜잭션 안에서 키를 지운다.** 지운 뒤 commit 전에 시작한 조회가 commit 전의 결과로 키를 다시 채운다. 모든 조합을 캐시하므로 지울 키를 찾으려면 `KEYS`·`SCAN`이나 따로 둔 키 목록도 든다.
- **commit 뒤에 키를 지운다.** 지우기가 실패하면 TTL까지 옛 결과가 남는다. 먼저 시작한 조회의 늦은 채움은 다음 조회가 읽을 바로 그 키에 옛 결과를 쓴다. 지울 키를 찾는 문제도 위와 같다. Spring의 `@CacheEvict(allEntries = true)`는 `KEYS`를 보낸다.
- **Redis의 세대 번호를 commit 뒤에 올린다.** 키를 찾는 문제와 늦은 채움은 풀린다. 그러나 `INCR`이 실패하면 TTL까지 옛 결과가 남는다. 삭제된 상품을 숨기려면 hit마다 페이지의 상품을 DB에서 다시 확인해야 하므로 hit에도 SQL이 남는다. 세대 번호가 사라졌을 때 쓴 적 없는 값에서 다시 시작하는 규칙, 세대는 master에서만 읽는 규칙, 시간을 다루는 신선도 정책과 그 테스트가 더 든다. 잠금을 아끼는 대신 실패 정책이 복잡해진다.
- **브랜드마다 revision 행을 둔다.** 비싼 전체 카탈로그의 페이지는 어느 쓰기에나 바뀌므로, 모든 쓰기가 전체의 행도 올려야 한다. 뜨거운 행은 그대로 남고, 두 행을 정해진 차례로 잠그는 규칙이 더 든다. 측정한 브랜드 필터 목록은 인덱스 뒤 모두 DB 안 1 ms 아래라서(8.4, 8.5), 그 캐시를 따로 살려 얻는 것이 적다.
- **차례만 캐시한다.** 페이지의 상품 id 차례만 두고 항목은 DB에서 읽는다. hit에도 항목 조회가 남고, 차례를 바꾸는 쓰기(가격, 좋아요)의 무효화 문제는 그대로다.

## 대가

- hit에도 SQL 하나(revision의 기본 키 조회)가 남는다. 과제는 이 확인의 비용을 hit 측정에 넣으라고 한다. miss의 SQL은 둘에서 셋이 된다.
- DB가 멈추면 캐시가 차 있어도 목록이 실패한다. 기존 오류 계약을 따른다.
- 여덟 쓰기가 모두 한 행에서 줄을 선다. 잠그지 않던 좋아요가 처음으로 잠금을 기다리고, 3초를 넘기면 409 `CONCURRENT_REQUEST`를 받는다(ADR 0018 규칙 7, 8). 이 행이 받아 낼 수 있는 쓰기의 수는 commit의 지연이 정한다.
- 어느 쓰기든 모든 목록 키를 무효로 만든다. 다른 브랜드의 키도, 좋아요 하나에도 그렇다. 좋아요가 잦으면 hit가 드물어진다.
- revision은 뒤로 가면 안 된다. 표를 비우거나 DB를 백업에서 되살리면 옛 키가 다시 읽힌다. 테스트는 DB를 비울 때 Redis도 비우고, 운영에서 DB를 되살리면 목록 캐시의 키를 지운다. 공유 Redis에 `FLUSHALL`을 보내지 않는다.
- 목록을 바꾸는 쓰기가 새로 생기면 revision을 올려야 한다. 잊어도 오류가 나지 않고 옛 결과가 조용히 남는다. 쓰기 경로마다의 장면 테스트가 지킨다. 올리기가 마지막 SQL이라는 것도 문장의 차례를 보는 테스트만 지킨다.

## 다시 볼 조건

- revision 행에서 잠금 대기나 409가 실제로 관찰되거나, 좋아요가 잦아 hit가 드물면 좋아요를 이 행에서 떼어 낸다. 좋아요 수를 캐시한 값에서 빼고 hit마다 따로 세거나, 좋아요 수를 비정규화한다(카탈로그 설계 5.28의 A).
- 상품 상세도 캐시하면 상세의 무효화를 따로 정한다. 이 행을 같이 쓰면 상세의 hit도 모든 쓰기에 무효가 된다.
- commerce-batch나 commerce-streamer가 상품, 브랜드, 좋아요를 바꾸기 시작하면 그 쓰기도 revision을 올려야 한다.

## 바꾸는 결정

ADR 0018 규칙 3과 ADR 0019 규칙 3의 잠금 순서, 그리고 0019의 경로 표 끝에 revision 행을 더한다. ADR 0018 규칙 1의 "좋아요는 상품을 바꾸지 않으므로 잠그지 않는다"는 그대로지만, 좋아요는 이제 revision 행을 잠근다. ADR 0016의 "모든 엔티티는 `BaseEntity`를 상속한다"에 revision 행이라는 예외가 생긴다. 이 ADR들과 카탈로그 설계 5.28, 5.32의 2026-10-15 메모, 8절 머리말은 구현하는 작업에서 원문을 두고 날짜 메모를 단다. 키, TTL, 직렬화, Redis 대기 한도 같은 이번 인터뷰의 다른 결정은 카탈로그 설계 8절에 캐시 범위·변경 책임·장애 계약으로 적는다.
