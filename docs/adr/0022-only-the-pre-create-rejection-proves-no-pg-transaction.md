# PG 거래가 없다는 증거는 정확한 생성 전 거절뿐이고, 생성 요청은 다시 보내지 않는다

과제는 응답을 잃은 결제를 실패로 보지 말라고 한다. 발송을 영속 기록한 뒤에는 생성 요청을 자동으로 다시 보내지 않고, 재시작 뒤에는 기존 거래를 조회한다. HTTP client, 프록시, 회복 라이브러리의 숨은 재시도도 끈다. 효과 0건의 증거는 로컬 테스트 PG가 명시적으로 약속하는 생성 전 거절(422, `TEST_PG_REJECTED_BEFORE_CREATE`, `transactionCreated: false`) 하나다. 시간 초과, 본문 없는 422, 다른 code의 4xx와 5xx, 잘못된 JSON, 조회의 404와 빈 목록은 그 증거가 아니다. 조회 0건, 2건 이상, 금액이나 식별자의 불일치에는 결과 미확인과 충돌을 남기고 다시 보내지 않는다.

무엇이 "보내지 않았다"의 증거인지는 코드 곳곳의 작은 분기에서 갈린다. 예외 하나를 실패로 옮기는 catch, 기본값으로 켜진 클라이언트의 재전송, 0건을 "없음"으로 읽는 조회가 모두 이중 결제가 된다.

1. **결제는 결과 미확인으로 시작하고, 생성 요청은 결제마다 한 번만 나간다.** 결제를 결과 미확인으로 저장한 뒤 PG를 부른다(2단계의 TX A). 그 뒤로는 시간 초과, 연결 끊김, 5xx, 재시작 어느 것도 생성 요청을 다시 보낼 이유가 되지 않는다. 결과는 조회와 대사로만 알아낸다.
2. **PG 거래가 없다는 증거는 정확한 생성 전 거절 하나다.** 어댑터는 422, 정확한 `code`, boolean `false`를 모두 확인할 때만 `Rejected(PgRejection)`로 옮긴다. 보낸 것과 같은 `orderId`와 `amount`인지는 `Payment.reject`가 본다([ADR 0021](./0021-payment-is-its-own-aggregate-and-slice.md)). 맞지 않으면 충돌이다.
3. **나머지는 모두 결과 미확인이다.**
   - 시간 초과, 연결 끊김, 본문 없는 422, 다른 code의 4xx, 5xx, 읽을 수 없는 본문, 모르는 PG 상태 문자열: 생성은 `Unknown`, 조회는 `Unavailable`이다. 둘 다 도메인에 들어가지 않는다.
   - 연결 풀에서 연결을 얻지 못한 생성도 결과 미확인이다. 보내지 않은 것이 확실하지만, 생성 전 거절만 증거로 삼는 규칙에 두 번째 길을 들이지 않는다.
   - 조회의 404와 빈 목록은 `Found(빈 목록)`이고, 대사에서 아무것도 바꾸지 않는다. PG 거래가 아직 보이지 않거나 생성 요청이 아직 오는 중일 수 있다.
4. **포트는 PG의 결과를 던지지 않는다.** `requestPayment`는 `Accepted`, `Rejected`, `Unknown`을, 두 조회는 `Found`, `Unavailable`을 값으로 돌려준다. 어댑터는 `retrieve()` 대신 `exchange`로 응답을 받아 상태 코드를 값으로 다룬다. 전송 예외(`ResourceAccessException`)와 해석 오류는 catch 하나가 결과 미확인으로 옮긴다. 예외를 실패로 옮기는 catch가 생길 자리가 없다.
5. **클라이언트의 숨은 재전송을 모두 끈다.** Apache HttpClient 5를 `disableAutomaticRetries()`와 `disableRedirectHandling()`으로 만든다. 기본값이면 429와 503에 POST를 한 번 더 보내고, 307과 308에는 본문까지 복사해 다시 보낸다. Boot의 HTTP client 스타터를 쓰지 않고 `RestClient`를 직접 만든다.
6. **계약 테스트가 재전송 경로마다 PG가 받은 요청 수를 센다.** 503에 POST 1번, 307에 POST 1번, 끊긴 GET에 GET 1번이다. 이 테스트는 운영의 시간 제한(연결 500 ms, 응답 1 s)으로 돈다. HttpClient는 응답 시간 제한이 재시도 간격 1초보다 짧으면 503 재시도를 건너뛰므로, 테스트 프로필의 200 ms에서는 스위치를 지워도 테스트가 통과한다.
7. **3단계의 재시도와 서킷 브레이커는 조회에만 씌운다.** 포트 하나가 생성과 조회를 함께 가지므로([ADR 0021](./0021-payment-is-its-own-aggregate-and-slice.md)), 어댑터 안에서 조회 메서드만 감싼다. 대사와 재시작이 생성을 0번 보낸다는 것은 장면 테스트가 PG가 받은 생성 수로 확인한다.

## 고르지 않은 것

- **시간 초과나 5xx를 실패로 본다.** 저장한 뒤 응답을 잃은 PG 거래가 나중에 성공하면, 예약을 돌려준 주문에서 돈이 빠져나간다. 고객이 다시 결제하면 두 번 낸다.
- **같은 PG 주문 번호로 생성을 다시 보낸다.** 테스트 PG는 같은 주문 번호의 생성을 하나로 합친다고 약속하지 않는다. 과제도 금한다.
- **조회 0건을 거래 없음으로 본다.** 0건은 "아직 보이지 않는다"와 구별되지 않는다. 그렇게 끝낸 결제 뒤에 늦게 도착한 생성이 성공하면 위와 같다.
- **연결을 얻지 못한 생성을 실패로 본다.** 그 예외는 보내지 않았다는 증거다. 그러나 증거가 HttpClient의 예외 타입과 Spring이 그것을 감싸는 방식에 달려 있어, 라이브러리를 올리거나 바꾸면 조용히 틀어질 수 있다. 과제도 생성 전 거절만 증거로 둔다.
- **생성 포트와 조회 포트를 나눈다.** 조회 포트만 재시도에 넘길 수 있으므로, 생성을 다시 보내지 않는다는 것을 타입이 지킨다. 1차 인터뷰에서 골랐다가, PG 하나를 감싸는 게이트웨이 하나가 결제 쪽의 관용에 맞아 3차에서 합쳤다. 그 보호는 규칙 6과 7이 맡는다.

## 대가

- 생성이 PG에 닿지 않았거나 PG가 잃은 결제는 결과 미확인에서 끝나지 않는다. 대사가 0건을 받아도 그대로이므로 예약도 남는다. 과제는 조회 한도를 다 쓴 것도 새 결제의 근거가 아니라고 하므로, 이 결제를 끝내는 것은 사람의 몫이다. PR에 남은 한계로 적는다.
- 응답 시간 제한 1초는 읽기 한 번마다의 한도이고 호출 전체의 기한이 아니다.
- 계약 테스트에 1.5초를 기다리는 장면이 하나 있다. (2026-10-20: 연결 풀을 얻지 못한 생성의 장면도 멈춘 생성으로 풀을 채운다. 그 장면은 풀의 연결을 하나로 줄인 `ExhaustedPoolPaymentGatewayTest`에 있어, 컨텍스트를 하나 더 띄우고 응답 한도 1초를 한 번 더 기다린다.)
- HTTP client를 바꾸거나 스타터를 들이는 변경은 숨은 재전송을 다시 켤 수 있다. 계약 테스트의 요청 수가 지킨다.

## 다시 볼 조건

- PG가 같은 키나 같은 주문 번호의 생성을 하나로 합친다고 약속하면(예: Toss의 `Idempotency-Key`), 같은 키로 생성을 다시 보내는 것을 다시 견준다.
- PG가 "이 주문 번호의 거래는 없고 앞으로도 없다"를 조회로 확정해 주면, 0건에 머무는 결과 미확인을 끝낼 수 있다.
- PG 앞에 프록시나 게이트웨이가 들어오면 그것의 재시도도 끈다.

## 바꾸는 결정

[ADR 0005](./0005-no-request-idempotency-until-a-retrying-caller.md)는 자동으로 재시도하는 호출자(외부 결제 연동)가 생기면 요청 멱등성을 다시 연다고 했다. 결제를 시작하는 요청이 멱등 키를 받으므로 그 조건이 찼다. 확정 요청의 계약은 2단계가 0005를 다시 열어 정한다.
