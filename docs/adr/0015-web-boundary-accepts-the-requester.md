# 웹 경계가 요청자를 받아들이고 application은 사용자 식별자를 믿는다

요청자는 API 게이트웨이가 요청 헤더에 실어 준 식별자로 알아낸 사용자다(`CONTEXT.md`). 실제 게이트웨이 뒤라면 서비스는 그 식별자를 믿는다. 그러나 2주차 과제는 사용자 식별이 빠진 요청과 없는 사용자의 요청을 함께 거절하라고 한다([포인트·주문 설계 2절](../design/points-orders.md) "사용자 식별 누락·없는 사용자를 거절하고"). 지금까지는 application이 그 일을 했다. 요청자를 받는 유스케이스 아홉 곳(좋아요 셋, 주문 넷, 포인트 둘)이 각자 `UserFinder.checkExists`를 불렀다([카탈로그 설계 5.27](../design/catalog.md)).

**이 로컬 구성에서는 웹 경계가 게이트웨이를 대신한다.** 컨트롤러가 돌기 전에 `adapter.webapi`의 `RequesterIdArgumentResolver`가 `@RequesterId` 파라미터를 채운다. `X-USER-ID`가 없으면 401, 숫자가 아니면 400, 그 사용자가 없으면 401이다. 사용자가 있는지는 사용자 조각의 `UserFinder.exists(userId): Boolean`에 묻고, 그것을 부르는 곳은 이 resolver 하나다. application은 받은 `userId`를 믿고 다시 확인하지 않는다. `users` 테이블은 신원 서비스의 사용자를 이 서비스가 들고 있는 사본으로 남는다. 외래 키가 가리키는 곳이고, "이 사용자가 있는가"에 답하는 곳이다.

- 경로의 사용자와 요청자를 견주는 403([카탈로그 설계 5.30](../design/catalog.md))은 그대로 `UserLikeApi`에 있고, 받아들인 요청자와 견준다. 없는 사용자는 경로와 무관하게 401이다. 인증이 인가보다 앞선다.
- application이 요청자를 믿으므로 사용자를 가리키지 않는 행은 DB가 막는다. 스칼라 참조의 외래 키를 만드는 `scalar-foreign-keys.sql`(옛 `order-foreign-keys.sql`)에 `FK_LIKES_USER`와 `FK_LIKES_PRODUCT`를 더했다. 주문에는 이미 `FK_ORDERS_USER`가 있고, 포인트 계정의 `FK_POINT_ACCOUNT_USER`는 연관에서 Hibernate가 만든다.

## 고르지 않은 것

- **믿기만 한다.** 게이트웨이 뒤의 서비스라면 맞는 모양이지만 과제의 "없는 사용자를 거절"을 놓친다.
- **게이트웨이를 그대로 흉내 내고 `users` 테이블을 없앤다.** 사용자를 이 서비스 밖의 것으로 두면 포인트 계정을 언제 누가 만드는지가 다시 열린다. 지금은 사용자를 준비할 때 0원 계정을 함께 만든다([포인트·주문 설계 5.9](../design/points-orders.md)). 외래 키가 가리킬 곳도 사라진다.
- **application에 검사를 둔다(지금까지의 5.27).** 요청자를 받는 조회마다 사용자 확인이 묶인다. 그래서 여러 조각이 함께 쓰는 조회는 같은 사용자를 거듭 확인하게 된다. 주문 확정이라면 포인트 차감이 자기 확인을 따로 한다. [#94](https://github.com/giwankim/loop-pack-be-l2-vol5-kotlin/issues/94)가 Finder를 순수한 조회로 만들려면 이 묶임이 먼저 풀려야 한다.

## 대가

- Controller를 거치지 않고 application을 부르는 쪽(배치, 컨슈머)은 사용자 확인을 받지 않는다. 층은 서로를 거치지 않고도 불릴 수 있으니 검사를 안쪽에 두라는 [카탈로그 설계 5.25](../design/catalog.md)를 요청자 확인에 한해 접는다. 그런 호출자가 넘기는 `userId`는 그 호출자가 책임진다. 없는 사용자의 행은 외래 키가 거절하고, 읽기는 빈 조각이나 `POINT_ACCOUNT_MISSING`으로 답한다.
- 검사 차례의 귀퉁이가 바뀐다. Spring은 인자를 파라미터 차례로 해석하고 `@RequesterId`가 본문보다 앞에 있다. 그래서 요청자가 없거나 없는 사용자인 요청은 본문이 잘못되어도 400이 아니라 401이다. 전에는 본문의 400이 앞섰다([포인트·주문 설계 12.3](../design/points-orders.md)). 두 잘못을 함께 보내는 요청의 status를 정하는 요구는 없고, 테스트도 한 가지 잘못만 보낸다.
- 요청자를 받는 요청은 읽기 트랜잭션을 하나 더 연다. resolver의 `exists`는 컨트롤러가 부르는 유스케이스의 트랜잭션 밖에서 돈다. 요청마다 나가는 쿼리 수는 같다.
- 반복 `ddl-auto=create`에서 스크립트의 외래 키가 표를 지우는 차례에 기댄다. 2026-10-08에 compose MySQL로 두 번 연달아 띄워 확인한 결과는 [포인트·주문 설계 8.2](../design/points-orders.md)에 있다.

## 다시 볼 조건

- 사용자가 실제 신원 서비스로 옮겨 가면 사용자 조각을 지우고 포인트 계정을 어떻게 만들지 정한다(포인트·주문 설계 5.9). 그때 웹 경계는 게이트웨이가 넣어 준 식별자를 믿기만 한다.
- Controller를 거치지 않고 요청자의 식별자를 넘기는 호출자가 생기면 그 입구에도 같은 확인을 둔다.

## 대체하는 결정

[카탈로그 설계 5.27](../design/catalog.md)의 선택 A. 이번 모양은 5.27이 대안 C로 적고 "식별이 필요한 엔드포인트가 넷을 넘을 때" 다시 보기로 한 것이다. 지금은 아홉이다. 5.27, 5.29, 5.30과 포인트·주문 설계의 해당 절은 원문을 그대로 두고 날짜 메모를 달았다.
