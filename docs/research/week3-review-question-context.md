# Week 3 review-question context

Checked 2026-10-09 against the current checkout. This is question-drafting context, not a full review; tests were inspected but not run in this session.

## Current decisions

- **Brand deletion is synchronous soft deletion in one transaction.** `BrandModifyService.delete` exclusively locks Brand, calls Product deletion, then marks Brand deleted. Product deletion locks active Products and calls each entity's `delete()` before `saveAll`. Zero-stock Products are included; already deleted Products retain their timestamps. Sources: [ADR 0017](../adr/0017-brand-delete-changes-brand-and-its-products-in-one-transaction.md), [BrandModifyService](../../apps/commerce-api/src/main/kotlin/com/loopers/application/brand/BrandModifyService.kt#L45-L55), [ProductModifyService](../../apps/commerce-api/src/main/kotlin/com/loopers/application/product/ProductModifyService.kt#L79-L87).
- **The locks serve different competing writers.** Registration holds Brand's shared lock; deletion's exclusive Brand lock coordinates with registration. Product locks coordinate with existing Product updates, stock updates and confirmation. Sources: [Product registration](../../apps/commerce-api/src/main/kotlin/com/loopers/application/product/ProductModifyService.kt#L33-L46), [ADR 0018](../adr/0018-pessimistic-row-locks-in-one-global-order.md).
- **Separate transactions change the consistency contract.** ADR 0017 rejects asynchronous after-commit Product deletion because a later failure cannot roll back an already committed Brand deletion. Synchronous events within the original transaction are a separate alternative. High Product counts are an explicit reconsideration condition; splitting transactions is not the only option recorded. Source: [ADR 0017](../adr/0017-brand-delete-changes-brand-and-its-products-in-one-transaction.md).
- **Confirmation locks Order → Products by ascending ID → PointAccount.** It does not lock Brand; Brand deletion's atomic cascade supports checking Product availability alone. Queries and Order creation do not all acquire these locks. Sources: [OrderModifyService](../../apps/commerce-api/src/main/kotlin/com/loopers/application/order/OrderModifyService.kt#L49-L85), [ADR 0019 lock-path table](../adr/0019-order-and-point-account-rows-locked-on-first-read.md).
- **Conditional UPDATE was rejected for stale managed entities and moving stock rules into SQL.** This is the project's rationale, not a claim that conditional updates cannot coexist safely with JPA. Source: [ADR 0018 alternatives](../adr/0018-pessimistic-row-locks-in-one-global-order.md). Spring Data documents that modifying queries can leave outdated entities in the context and that clearing can discard pending changes: [official modifying-query documentation](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html#jpa.modifying-queries).

## Existing test coverage

- Tests already use committed fixtures, independent worker calls, start gates, outcome counts and fresh transactions for final-state assertions. Forced schedules hold one operation with a spy/latch. Waiting is inferred from one-second non-completion, not direct database lock-state observation. Source: [BaseCommittingApplicationServiceTest](../../apps/commerce-api/src/test/kotlin/com/loopers/support/test/BaseCommittingApplicationServiceTest.kt#L20-L47).
- Coverage includes registration/deletion in both directions; Product writes/cascade; scarce stock; repeated confirmation of one Order; different Products sharing one account; charge/payment; confirmation/deletion. Tests assert stock and point conservation. Sources: [BrandRegisterConcurrencyTest](../../apps/commerce-api/src/test/kotlin/com/loopers/application/brand/provided/BrandRegisterConcurrencyTest.kt), [OrderConfirmerConcurrencyTest](../../apps/commerce-api/src/test/kotlin/com/loopers/application/order/provided/OrderConfirmerConcurrencyTest.kt).
- A negative control forces two separate JDBC connections to read stock 5 and both write absolute stock 4. Cascade rollback flushes real SQL before injecting failure and rereads the original snapshot. Sources: [LostUpdateControlTest](../../apps/commerce-api/src/test/kotlin/com/loopers/application/order/provided/LostUpdateControlTest.kt#L43-L61), [BrandRegisterRollbackTest](../../apps/commerce-api/src/test/kotlin/com/loopers/application/brand/provided/BrandRegisterRollbackTest.kt#L162-L166).

## Wording for questions

Use “브랜드·상품 논리 삭제,” not language suggesting foreign-key or JPA remove cascade. Say “이미 커밋된 브랜드 삭제를 함께 롤백할 수 없어,” rather than merely “롤백이 어렵다.” Ask which workload and conflict indicators justify changing pessimistic locking; avoid asserting inefficiency without measurements. For conditional writes, ask about “벌크 갱신 후 엔티티 상태 불일치와 flush·clear의 처리 기준,” rather than losing the persistence context. Since relevant tests exist, ask what competing writers, schedules and assertions should be added beyond current tests and load testing.
