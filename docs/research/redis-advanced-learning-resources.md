# Learning cache invalidation and advanced Redis usage

Researched 2026-10-16 against publisher/author pages, official Redis documentation, and first-party engineering articles and papers. The ordering and exercises below are a practical learning recommendation for a Kotlin/Spring backend developer. They are not application changes or a claim that the exercises have been run.

## Recommended route

Use **cache-consistency case studies for reasoning**, then **one Redis book/course for breadth**, with **official Redis docs for precise behavior**. Cache invalidation extends beyond Redis commands: readers, database writers, cache fills, invalidation delivery, and failures form a protocol.

The concern about book age is justified: Manning dates Josiah Carlson's *Redis in Action* to **June 2013**. Keep it for its worked examples, but pair it with current documentation and the resources below. [Publisher](https://www.manning.com/books/redis-in-action)

## Official Redis docs to study alongside the path

These links use `latest`; check the Redis server/client version before adopting a command or feature. Redis Open Source, Redis Cloud, and Redis Software capabilities can differ.

| Topic | Read and reason about | Concrete takeaway |
| --- | --- | --- |
| Client-side caching and invalidation races | [Client-side caching reference](https://redis.io/docs/latest/develop/reference/client-side-caching/), especially **Avoiding race conditions**, **What to do when losing connection**, and **Other hints** | When data and invalidations use separate connections, an invalidation can arrive before an older read reply. Redis documents an in-progress placeholder so that reply cannot repopulate the removed entry. A single connection preserves ordering for this specific race. Flush local data on invalidation-connection loss; bound local memory/TTL. This tracks Redis-to-client copies; it is not a database-to-Redis invalidation protocol. |
| Lost invalidations | [Pub/Sub delivery semantics](https://redis.io/docs/latest/develop/pubsub/#delivery-semantics) and [keyspace notifications](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/) | Pub/Sub is at-most-once; disconnected subscribers lose messages. Keyspace notifications use Pub/Sub and are disabled by default. A broadcast-only invalidation design needs an explicit recovery/freshness policy. |
| Expiration, eviction, and memory | [Key eviction](https://redis.io/docs/latest/develop/reference/eviction/) | Distinguish TTL expiration from eviction under memory pressure. Compare LRU/LFU and `allkeys-*` versus `volatile-*`; inspect hits, misses, evictions, and expirations. `maxmemory` does not count some replication/AOF buffers, so reserve RAM rather than setting it equal to the machine's entire memory. |
| Replica reads and failover | [Replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/) and [`WAIT`](https://redis.io/docs/latest/commands/wait/#consistency-and-wait) | Replication is asynchronous by default. `WAIT` reports acknowledged copies of earlier writes on the current connection; check its returned count. It improves data safety but does not make Redis strongly consistent or guarantee no acknowledged-write loss during failover. |
| Atomic multi-command logic | [Redis programmability](https://redis.io/docs/latest/develop/programmability/) | Learn Lua/EVAL and Redis Functions (introduced in Redis 7), including script-cache/deployment differences. Their execution is atomic within Redis, but blocks other server activity while running. A Redis script does not make a separate database transaction atomic with Redis. |
| Locks, lease expiry, and fencing | [Distributed locks with Redis](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) together with [Kleppmann's analysis](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html) — 2016-02-08 | First distinguish reducing duplicate work from protecting correctness. Study a paused holder resuming after lease expiry and whether the protected store rejects older fencing tokens. The current Redis page itself recommends fencing tokens and links the critique and antirez's response. Evaluate the assumptions, not just the lock-acquisition code. |

For a Kotlin/Spring implementation, translate the protocol into your actual transaction, client, and process model after the reading. A library's convenient cache annotation is not evidence that stale fills, process-local copies, or missed invalidations have been handled. This is an application-design inference from the failure models above, not a claim about a specific Spring version or this checkout.

### One useful branch beyond caching: Streams

Study [Redis streaming](https://redis.io/docs/latest/develop/use-cases/streaming/) after Pub/Sub. Learn `XREADGROUP`, pending entries, `XACK`, and `XAUTOCLAIM`: acknowledgment and reassignment allow recovery from a failed consumer. Then crash a worker after its side effect but before acknowledgment and make the side effect idempotent when it is delivered again. Also test retention outrunning a slow consumer. These are recovery exercises; choosing Streams alone does not create an atomic database/cache update or end-to-end exactly-once effects. Redis provides [Java/Lettuce examples](https://redis.io/docs/latest/develop/use-cases/streaming/java-lettuce/) for a later implementation step.

## Three exercises that turn the reading into understanding

Use a small cache-aside read over one database record, an isolated Redis instance, and deterministic barriers/latches rather than timing guesses. These are suggested labs, not completed validation.

1. **Reproduce stale repopulation.** Start a reader that loads database version 1, pause it before cache fill, commit version 2 in another request, and invalidate. Release the old reader and inspect the resulting cache. Then compare an explicitly defined version/lease approach. **Done when:** a trace explains the broken interleaving and the revised protocol's invariant; tests include rollback, deletion, and missing/evicted version metadata. Read Meta, then Memcache leases.
2. **Expire one hot key under load.** Synchronize concurrent misses and measure source query count, p95 latency, and failures. Compare ordinary cache-aside, request coalescing, and early refresh under the same workload. Include low traffic and a slow refresher, not just peak throughput. **Done when:** you can quantify backend work and explain freshness, wait-time, and duplicate-refresh tradeoffs. Read AWS and Cloudflare.
3. **Break invalidation and cache availability.** Disconnect one local-cache subscriber during a write, reconnect it, and observe how it recovers. Separately stop Redis and restart it cold while applying load. **Done when:** stale duration, cache timeouts, source concurrency, and recovery load are visible; fallback remains bounded. For server-assisted client-side caching, verify the documented flush-on-disconnect behavior separately from ordinary Pub/Sub. Read the Redis client-side-caching/Pub/Sub docs and AWS.

After these three, work through the operations course's failover, memory-pressure, and latency labs. The aim is to explain both **when an answer can be stale** and **what happens to the database when the cache stops helping**.

## Company engineering case studies — expansion researched 2026-10-16

Company engineering blogs are especially useful for advanced Redis study because they expose the workload, failure, and tradeoff behind a design. These are first-party technical accounts, read beyond search-result snippets. Dates below identify the architecture being described; an old design is not evidence of the company's current production stack. The Uber CacheFront series above remains the first Redis-specific consistency case study to read.

For this Kotlin/Spring learning path, start with **KakaoPay's stale-fill example → LINE's atomic processing → Figma's connection architecture**. Then choose a branch: Grab for a replicated local cache, Slack for backlog/backpressure, or Stripe for coordination beyond caching. GitHub and Discord are useful deeper comparisons rather than prerequisites.

For each chosen case, draw the read/write or producer/consumer sequence, identify the authoritative data, and inject one failure from the article. Add a small lab only after stating the invariant: for example, cap Redis connections during application scale-out, pause job workers until a queue exceeds its memory budget, or retry an aggregation chunk and inspect double counting. Compare the observed behavior with the original article's assumptions before adopting its design.
