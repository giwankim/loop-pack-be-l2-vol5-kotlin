# Circuit breaker and retry on Spring Boot 4.1

Researched 2026-10-19 against Maven Central metadata (POMs and Gradle module files), GitHub source at the release tags (Resilience4j `v2.4.0`, Spring Framework `v7.0.9`, Spring Boot `v4.1.1`, Spring Cloud Circuit Breaker `v5.0.3`), GitHub release notes and issues, Spring Initializr's live metadata, and the official reference docs. Statements are verified from the linked source unless they are marked **Inference**. Nothing here was run as application code. The only command run against this checkout was a read-only `./gradlew :apps:commerce-api:dependencyInsight`.

The target is the PG exercise: a breaker on the lookup path only (GET by transaction key, list by order id), bounded retry on lookups only (never on the POST that creates a payment), a fallback that returns stored state, a synchronous `RestClient`, Kotlin, and Boot 4.1.1.

[SCCB deps POM](https://repo1.maven.org/maven2/org/springframework/cloud/spring-cloud-circuitbreaker-dependencies/5.0.3/spring-cloud-circuitbreaker-dependencies-5.0.3.pom), [SCCB Resilience4j POM](https://repo1.maven.org/maven2/org/springframework/cloud/spring-cloud-circuitbreaker-resilience4j/5.0.3/spring-cloud-circuitbreaker-resilience4j-5.0.3.pom)

The maintainer's answer on [issue 305](https://github.com/spring-cloud/spring-cloud-circuitbreaker/issues/305) (2026-09-10): the switch to 2.4.0 + `resilience4j-spring-boot4` "will be part of the Spring Cloud 2026.0.0 release which is tentatively scheduled for release in November". **Inference:** no GA Spring Cloud train pairs Boot 4.1 with `resilience4j-spring-boot4`. [Factory L62](https://github.com/spring-cloud/spring-cloud-circuitbreaker/blob/v5.0.3/spring-cloud-circuitbreaker-resilience4j/src/main/java/org/springframework/cloud/circuitbreaker/resilience4j/Resilience4JCircuitBreakerFactory.java#L62), [`run()`](https://github.com/spring-cloud/spring-cloud-circuitbreaker/blob/v5.0.3/spring-cloud-circuitbreaker-resilience4j/src/main/java/org/springframework/cloud/circuitbreaker/resilience4j/Resilience4JCircuitBreaker.java#L97-L140). [Docs](https://docs.spring.io/spring-cloud-circuitbreaker/reference/spring-cloud-circuitbreaker-resilience4j/circuit-breaker-properties-configuration.html), [`TimeLimiterConfig`](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-timelimiter/src/main/java/io/github/resilience4j/timelimiter/TimeLimiterConfig.java#L14-L15)
- SCCB 5.0 also has a **Framework Retry** implementation (`spring-cloud-starter-circuitbreaker-framework-retry`). The docs say it opens "after a single failed execution (all retries exhausted) rather than counting individual retry attempts". [Docs](https://docs.spring.io/spring-cloud-circuitbreaker/reference/spring-cloud-circuitbreaker-framework-retry.html). **Inference:** it has no minimum sample size, failure-rate threshold or half-open probe count, so it cannot express requirement (a).

## 2. Annotation wiring on Boot 4

### AspectJ is required and is not transitive

- Boot 4.0: "To clarify the scope of `spring-boot-starter-aop`, it has been renamed to `spring-boot-starter-aspectj`." [Migration guide](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide#aop-starter-pom). No `spring-boot-starter-aop` exists for 4.0 GA or later. Its 4.x versions stop at 4.0.0-M2, and the 3.5.x line still publishes it. `spring-boot-starter-aspectj` 4.1.1 consists of `spring-boot-starter` + `spring-aop` + `aspectjweaver`, and it is BOM-managed. [starter-aop metadata](https://repo1.maven.org/maven2/org/springframework/boot/spring-boot-starter-aop/maven-metadata.xml), [starter-aspectj 4.1.1 POM](https://repo1.maven.org/maven2/org/springframework/boot/spring-boot-starter-aspectj/4.1.1/spring-boot-starter-aspectj-4.1.1.pom)
- `resilience4j-spring-boot4` declares `spring-boot-starter-aspectj` as **compileOnly**, so you get no AspectJ from it. [build.gradle L10](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring-boot4/build.gradle#L10)
- The Resilience4j aspects are registered only under `AspectJOnClasspathCondition`, which checks for `org.aspectj.lang.ProceedingJoinPoint`. Otherwise the only output is a **debug** log line, "Aspects are not activated because AspectJ is not on the classpath." The annotations are then silently inert. [Condition](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/utils/AspectJOnClasspathCondition.java#L24-L33), [aspect bean](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/circuitbreaker/configure/CircuitBreakerConfiguration.java#L91-L101)
- Boot's `AopAutoConfiguration` enables `@EnableAspectJAutoProxy(proxyTargetClass = true)` when `org.aspectj.weaver.Advice` is present. Setting `spring.aop.proxy-target-class=false` switches it to JDK proxies. [Source](https://github.com/spring-projects/spring-boot/blob/v4.1.1/core/spring-boot-autoconfigure/src/main/java/org/springframework/boot/autoconfigure/aop/AopAutoConfiguration.java), [docs](https://docs.spring.io/spring-boot/4.1/reference/features/aop.html)
- **This checkout (read-only `dependencyInsight`, 2026-10-19):** `org.aspectj:aspectjweaver:1.9.25.1` is already on `:apps:commerce-api` `runtimeClasspath`. The path is `spring-aspects:7.0.9` ← `spring-boot-data-jpa:4.1.1` ← `spring-boot-starter-data-jpa` ← `project ':modules:jpa'`, where `modules/jpa/build.gradle.kts` has `api(libs.springBootStarterDataJpa)`. So annotations would work today **only because of JPA**. **Inference:** this is exactly the "don't assume a starter already includes it" trap. Declare `spring-boot-starter-aspectj` explicitly where annotations are used.

### Proxies, self-invocation, Kotlin

- Self-invocation: "self invocation via an explicit or implicit `this` reference will bypass the advice." The documented remedies, in order of preference, are refactoring, self injection, and (discouraged) `AopContext.currentProxy()`. With CGLIB, "`final` classes cannot be proxied" and "`final` methods cannot be advised". [Spring AOP proxying](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html)
- kotlin-spring opens classes annotated with `@Component`, `@Async`, `@Transactional`, `@Cacheable` and `@SpringBootTest`. Through meta-annotations it also opens `@Configuration`, `@Controller`, `@RestController`, `@Service` and `@Repository`. "the class itself and all its members will become open". Neither Resilience4j's annotations nor Framework's `@Retryable` are in that list. [Kotlin all-open docs](https://kotlinlang.org/docs/all-open-plugin.html). In this repo, `build-logic/src/main/kotlin/loopers.kotlin-spring.gradle.kts` applies `libs.plugins.kotlin.spring`. **Inference:** put the annotated lookup methods on a `@Component`-family bean and call them from another bean. A class registered only through `@Bean` stays final, and CGLIB cannot proxy it.
- **Proving that a real proxy is applied (Inference):** a test can assert `AopUtils.isAopProxy(bean)` / `isCglibProxy(bean)` ([Javadoc](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/aop/support/AopUtils.html)). It should also assert the server-side call count, so a silently inert annotation fails the test.

### Aspect order and what one breaker sample is

Default order values in `resilience4j-spring6` 2.4.0, which the boot4 `*Properties` classes extend:

| Aspect | Default `*AspectOrder` | Source |
| --- | --- | --- |
| Retry | `Ordered.LOWEST_PRECEDENCE - 5` | [RetryConfigurationProperties L26](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/retry/configure/RetryConfigurationProperties.java#L26) |
| CircuitBreaker | `LOWEST_PRECEDENCE - 4` | [CircuitBreakerConfigurationProperties L23](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/circuitbreaker/configure/CircuitBreakerConfigurationProperties.java#L23) |
| RateLimiter | `LOWEST_PRECEDENCE - 3` | [RateLimiterConfigurationProperties L23](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/ratelimiter/configure/RateLimiterConfigurationProperties.java#L23) |
| TimeLimiter | `LOWEST_PRECEDENCE - 2` | [TimeLimiterConfigurationProperties L25](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/timelimiter/configure/TimeLimiterConfigurationProperties.java#L25) |

- Spring: "the aspect returning the lower value from `Ordered.getOrder()` … has the higher precedence", and "The highest precedence advice runs first 'on the way in'". [Advice ordering](https://docs.spring.io/spring-framework/reference/core/aop/ataspectj/advice.html). Retry has the lowest value, so it is outermost. That matches the documented `Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( Function ) ) ) ) )`.
- **Consequence:** with both annotations at the defaults, the breaker sees one sample per attempt. Issue 2383 reproduces this: with `maxAttempts=3`, `resilience4j.circuitbreaker.calls{kind="failed"}` = `3.0`. The maintainer (RobWin) keeps the default on purpose: "If a system is unavailable, but circuit breaker is still closed, then I want to count every request as a failure and not 3 or more retry attempts as a single failure. This would not prevent a retry storm." [Issue 2383](https://github.com/resilience4j/resilience4j/issues/2383). The issue quotes older values (-4/-3). 2.4.0 uses -5/-4, and the relative order is the same.
- To change the order, set `resilience4j.retry.retryAspectOrder`, `resilience4j.circuitbreaker.circuitBreakerAspectOrder`, etc. [Docs](https://resilience4j.readme.io/docs/getting-started-3). Watch out for the wording: the docs page says "the higher value = the higher priority". Spring's rule, and the boot3 README warning, say the **lower** value is outer. Both use the same example: `circuitBreakerAspectOrder=1`, `retryAspectOrder=2` puts the breaker outside, with one sample per logical call. [boot3 README](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring-boot3/README.adoc). The boot4 README has no such note; [PR 2444](https://github.com/resilience4j/resilience4j/pull/2444), which adds one, is still open.

## 3. Programmatic use (no AOP)

### Composition decides the sample unit

- `Decorators.ofSupplier(s).withCircuitBreaker(cb).withRetry(retry).decorate()`: each `with*` wraps the supplier built so far (`supplier = CircuitBreaker.decorateSupplier(circuitBreaker, supplier)`, then `supplier = Retry.decorateSupplier(retryContext, supplier)`). **The first `with*` is the innermost.** [Decorators L99-L107](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-all/src/main/java/io/github/resilience4j/decorators/Decorators.java#L99-L107). `Decorators` lives in `resilience4j-all` ("you will need the resilience4j-all dependency"). [Getting started](https://resilience4j.readme.io/docs/getting-started)
  - `withCircuitBreaker(cb).withRetry(retry)` puts Retry outside the breaker: **each attempt is a breaker sample**, the same as the annotation default.
  - `withRetry(retry).withCircuitBreaker(cb)` puts the breaker outside: **one sample per logical lookup**.
  - Without `resilience4j-all`, the same thing is `Retry.decorateSupplier(retry, CircuitBreaker.decorateSupplier(cb, supplier))`. `resilience4j-kotlin` adds `CircuitBreaker.executeFunction { }` / `Retry.executeFunction { }` and suspend/Flow variants. [kotlin CircuitBreaker.kt](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-kotlin/src/main/kotlin/io/github/resilience4j/kotlin/circuitbreaker/CircuitBreaker.kt), [kotlin Retry.kt](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-kotlin/src/main/kotlin/io/github/resilience4j/kotlin/retry/Retry.kt)
- Fallback: `Decorators.withFallback(listOf(...exception types), fn)` or a plain Kotlin `try/catch` around the decorated call. Keeping the fallback to "read stored state" is application code; the library cannot enforce it.

### CircuitBreakerConfig (2.4.0)

| Knob | Default | Verified behaviour |
| --- | --- | --- |
| `slidingWindowType` / `slidingWindowSize` | `COUNT_BASED` / 100 | Count-based means the last N calls; time-based means the last N seconds. [Docs](https://resilience4j.readme.io/docs/circuitbreaker) |
| `minimumNumberOfCalls` | 100 | With fewer calls recorded, the failure rate is not calculated ("will not transition to open even if all 9 calls have failed"). **For COUNT_BASED the effective minimum is `min(minimumNumberOfCalls, slidingWindowSize)`.** [CircuitBreakerMetrics L42-L59](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/internal/CircuitBreakerMetrics.java#L42-L59) |

### `CallNotPermittedException` inside a retry

- The retry module and the spring6 retry aspect have no special case for `CallNotPermittedException`; a grep of `resilience4j-retry/src/main` finds nothing. The default retry predicate is `throwable -> true`. **So when Retry wraps an OPEN breaker, every rejection is retried, and each one uses an attempt and waits the backoff.**
- **Inference:** a lookup against an OPEN breaker then makes 0 HTTP calls, 3 retry attempts and 2 back-off waits before reaching the fallback. Add `ignoreExceptions(CallNotPermittedException::class.java)` (or the property `ignore-exceptions`) to the lookup retry so that an OPEN breaker fails fast into the stored-state fallback. Assert this in a test.

## 4. Deterministic testing

### CircuitBreaker

- **Forced transitions:** `transitionToOpenState()`, `transitionToOpenStateFor(Duration)`, `transitionToHalfOpenState()`, `transitionToClosedState()`, and `reset()` ("Returns the circuit breaker to its original closed state, losing statistics"). [CircuitBreaker.java](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/CircuitBreaker.java)
- **Injectable clock:** `CircuitBreakerConfig.Builder.clock(Clock)` (default `Clock.systemUTC()`) drives the OPEN wait check `clock.instant().isAfter(retryAfterWaitDuration)` and the TIME_BASED window. A mutable test `Clock` advanced past `waitDurationInOpenState` therefore makes the next call open the HALF_OPEN transition without sleeping. `isAfter` is strict, so advance by more than the wait. Keep `automaticTransitionFromOpenToHalfOpenEnabled=false`, because the automatic path schedules on a real `ScheduledExecutorService`. [OpenState L699-L738](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/internal/CircuitBreakerStateMachine.java#L699-L738)
- **Slow calls ignore the clock by default:** `currentTimestampFunction` defaults to `clock -> System.nanoTime()`. To fake slow calls, also set `currentTimestampFunction({ it.millis() }, TimeUnit.MILLISECONDS)`. [Config L58](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/CircuitBreakerConfig.java#L58), [state machine L161](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/internal/CircuitBreakerStateMachine.java#L161)
- **Metrics:** `cb.metrics` exposes `numberOfBufferedCalls`, `numberOfFailedCalls`, `numberOfSuccessfulCalls`, `failureRate` (−1 below the minimum) and `numberOfNotPermittedCalls`. The not-permitted count "is only increased when the CircuitBreaker state is OPEN". Metrics belong to the current state: HALF_OPEN starts a fresh `CircuitBreakerMetrics`, so counts restart on that transition. For a cumulative trace, subscribe to `eventPublisher.onStateTransition / onError / onSuccess / onCallNotPermitted / onIgnoredError`. [Metrics + EventPublisher](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/CircuitBreaker.java#L940-L1040)
- **With the Boot module (Inference):** `resilience4j.circuitbreaker.*` properties cannot set a clock (the instance properties have no such field). A test `@Bean` of `CircuitBreakerConfigCustomizer` ([interface](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-framework-common/src/main/java/io/github/resilience4j/common/circuitbreaker/configuration/CircuitBreakerConfigCustomizer.java)) is the hook for one. ## 5. TimeLimiter and a synchronous RestClient

- TimeLimiter only decorates a `Future` supplier or a `CompletionStage` ("TimeLimiter has higher order decorator functions to decorate a `CompletionStage` or `Future`"). [Docs](https://resilience4j.readme.io/docs/timeout). On any other return type, the `@TimeLimiter` aspect throws `IllegalReturnTypeException(..., "CompletionStage expected.")` unless an extension (e.g. Reactor) handles the type. [TimeLimiterAspect L105-L108](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/timelimiter/configure/TimeLimiterAspect.java#L105-L108)
- `cancelRunningFuture` (default true) applies only on the `Future` path, where a timeout calls `future.cancel(true)`. The `CompletionStage` path just calls `future.completeExceptionally(TimeoutException)` and never cancels. [TimeLimiterImpl L50-L55, L175-L189](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-timelimiter/src/main/java/io/github/resilience4j/timelimiter/internal/TimeLimiterImpl.java#L50-L55)
- `CompletableFuture`: "this class has no direct control over the computation that causes it to be completed, cancellation is treated as just another form of exceptional completion." [JDK 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/CompletableFuture.html). The Kotlin helper `TimeLimiter.executeFunction { }` (new in 2.4.0) runs the block in `CompletableFuture.supplyAsync(block)`. [kotlin TimeLimiter.kt L92-L94](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-kotlin/src/main/kotlin/io/github/resilience4j/kotlin/timelimiter/TimeLimiter.kt#L92-L94). **Inference:** after a timeout, the blocking HTTP call keeps running on the common pool.
- Interrupts cancel a `FutureTask`, but JDK 25 documents a socket read as interruptible only when the socket is associated with a `SocketChannel`, or uses the default implementation **on a virtual thread**. [Socket](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/net/Socket.html). **Inference:** whether `cancel(true)` actually stops a `RestClient` call depends on the HTTP client and the thread type, so do not rely on it.
- **HTTP client timeouts are the bound on a synchronous call.** Boot 4.1 has global `spring.http.clients.connect-timeout` / `read-timeout` and per-group `spring.http.serviceclient.<group>.*` timeouts. It picks the client in this order: Apache HttpClient, Jetty, Reactor Netty, JDK `HttpClient`, `HttpURLConnection`. [Boot 4.1 RestClient docs](https://docs.spring.io/spring-boot/4.1/reference/io/rest-client.html), [HttpClientSettingsProperties](https://github.com/spring-projects/spring-boot/blob/v4.1.1/module/spring-boot-http-client/src/main/java/org/springframework/boot/http/client/autoconfigure/HttpClientSettingsProperties.java). **Inference:** for this exercise, use read and connect timeouts on the PG `RestClient` and skip TimeLimiter. If slowness should open the breaker, use `slowCallDurationThreshold` / `slowCallRateThreshold` for that.

## 6. Spring Framework 7 built-in resilience

- **Contents (since 7.0):** `org.springframework.resilience.annotation.@Retryable` and `@ConcurrencyLimit`, enabled by `@EnableResilientMethods` (or by registering `RetryAnnotationBeanPostProcessor` / `ConcurrencyLimitBeanPostProcessor` beans), plus programmatic `org.springframework.core.retry.RetryTemplate` / `RetryPolicy`. [Docs](https://docs.spring.io/spring-framework/reference/7.0/core/resilience.html). Watch for the name clash: `org.springframework.core.retry.Retryable` is the functional interface passed to `RetryTemplate`, not the annotation.
- **Attempt semantics:** "`total attempts = 1 initial attempt + maxRetries attempts`. For example, if `maxRetries` is set to `4`, the `@Retryable` method will be invoked at least once and at most 5 times." The default is `maxRetries = 3`, which is **up to 4 calls**. `RetryTemplate`/`RetryPolicy` have the same rule. [Docs](https://docs.spring.io/spring-framework/reference/7.0/core/resilience.html), [Retryable L118](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-context/src/main/java/org/springframework/resilience/annotation/Retryable.java#L118)
- **Back-off:** `delay` 1000 ms, `multiplier` 1.0, `maxDelay` unlimited, `jitter` 0, and `timeout` 0 (none; since 7.0.2; bounds the total elapsed time including delays). Jitter is "randomly subtracted or added to the calculated delay … but never below the base `delay()` or above `maxDelay()`. If a multiplier is specified, it is applied to the jitter value as well." With `delay = 0` and positive jitter, the delay is random in `0..min(jitter, maxDelay)`. [Retryable](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-context/src/main/java/org/springframework/resilience/annotation/Retryable.java#L137-L263)
- **What to retry:** `includes`/`value` and `excludes` are "matched against an exception thrown by a failed invocation as well as nested causes". A `MethodRetryPredicate` (annotation) or `Predicate<Throwable>` (builder) is "applied after `includes` and `excludes`". There is no result-based retry: every filter is exception-based (attribute list in the same file).
- **Boot 4.1.1 auto-configures none of the annotation support.** The v4.1.1 source has no reference to `org.springframework.resilience`. `org.springframework.core.retry` appears only in `RetryPolicySettings` and the AMQP/Kafka/Redis listener retry settings. So `@EnableResilientMethods` must be declared explicitly. [RetryPolicySettings](https://github.com/spring-projects/spring-boot/blob/v4.1.1/core/spring-boot/src/main/java/org/springframework/boot/retry/RetryPolicySettings.java)
- **Proxying:** `RetryAnnotationBeanPostProcessor` is an `AbstractBeanFactoryAwareAdvisingPostProcessor` with an `AnnotationMatchingPointcut`, so it needs plain Spring AOP and no AspectJ. It calls `setBeforeExistingAdvisors(true)`, which on an already-proxied bean means `advised.addAdvisor(0, advisor)`. [RetryAnnotationBeanPostProcessor L56-L70](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-context/src/main/java/org/springframework/resilience/annotation/RetryAnnotationBeanPostProcessor.java#L56-L70), [AbstractAdvisingBeanPostProcessor L94-L99](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-aop/src/main/java/org/springframework/aop/framework/AbstractAdvisingBeanPostProcessor.java#L94-L99). `@EnableResilientMethods(proxyTargetClass = false, order = LOWEST_PRECEDENCE - 1)` by default. [Source L60-L69](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-context/src/main/java/org/springframework/resilience/annotation/EnableResilientMethods.java#L60-L69). **Inference:** if Framework `@Retryable` and Resilience4j `@CircuitBreaker` sit on the same method, Framework retry becomes the outermost advisor. Each retry is then a breaker sample, and an OPEN breaker's `CallNotPermittedException` is retried unless listed in `excludes`. The proxy type (JDK vs CGLIB) under Boot's global class-proxying default was not traced end to end, so assert it in a test. Self-invocation limits are the same as for any Spring proxy.
- **Observability:** "Spring publishes a `MethodRetryEvent` for every exception coming out of the target method" (`MethodRetryEvent` since 7.0.3), and `@RecordApplicationEvents` can capture it. `RetryTemplate` takes a `RetryListener` with `onRetryableExecution`, `beforeRetry`, `onRetrySuccess`, `onRetryFailure`, `onRetryPolicyExhaustion`, `onRetryPolicyInterruption` and `onRetryPolicyTimeout`. `RetryState.getRetryCount()`: "0 indicates the initial invocation, 1 the first retry attempt". `RetryTemplate` sleeps with a direct `Thread.sleep(sleepTime)` and has no sleeper hook, so tests set `delay = 0`. [RetryTemplate L126-L160](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-core/src/main/java/org/springframework/core/retry/RetryTemplate.java#L126-L160), [RetryState L42](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-core/src/main/java/org/springframework/core/retry/RetryState.java#L42)
- **No circuit breaker:** confirmed by the empty grep of the v7.0.9 tree. Spring Cloud's docs call Framework retry "stateless" and build their own breaker on top of it (§1).
- **Spring Retry, for comparison:** archived, and its `maxAttempts` counts the initial try ("setting this property to 3 means 3 attempts total (initial + 2 retries)"). [SimpleRetryPolicy @ v2.0.13](https://github.com/spring-projects/spring-retry/blob/v2.0.13/src/main/java/org/springframework/retry/policy/SimpleRetryPolicy.java#L154-L157)

**Inference: recommendation.** **Option A** fits best. The assignment grades exact semantics (which call is a breaker sample, real call counts, CLOSED → OPEN → HALF_OPEN → recovered/re-opened). A keeps those in plain Kotlin that a test can drive with a fake `Clock` and an HTTP mock: it adds two pinned artifacts and no AOP. For the "one sample per logical lookup" reading, nest Retry inside the breaker. For the maintainer's "every request counts" reading, nest Retry outside the breaker and add `ignoreExceptions(CallNotPermittedException)` on the retry. Whichever you pick, state it in the PR and pin it with a test. Choose **B** only if annotations are themselves a goal. Then set `circuitBreakerAspectOrder`/`retryAspectOrder` explicitly, add `spring-boot-starter-aspectj`, and keep the proxy and count assertions. **C** is reasonable if "use what the platform ships" matters more than one vocabulary. **D** and **E** don't fit Boot 4.1.1 today.
